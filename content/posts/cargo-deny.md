ยิ่งโปรเจกต์ของเราใหญ่ขึ้น แน่นอนว่าจำนวน dependency ที่ดึงมาใช้ก็ยิ่งเพิ่มขึ้นเป็นเงาตามตัว และในความเป็นจริง เราแทบไม่มีเวลามานั่งอ่านโค้ดของ crate ทุกตัวที่ติดตั้งลงไปใช่ไหมครับ `cargo-deny` จึงเป็นเครื่องมือสำคัญที่เข้ามาทำหน้าที่เป็น **"ด่านตรวจ"** คอยสแกนห่วงโซ่อุปทาน (Supply Chain) ของโปรเจกต์ โดยรันเป็นส่วนหนึ่งของ CI/CD pipeline หรือรันในเครื่อง local เพื่อดักจับสิ่งผิดปกติก่อนที่โค้ดอันตรายจะหลุดไป

## cargo-deny คืออะไร?

`cargo-deny` คือ Cargo plugin สำหรับตรวจสอบ (lint) dependency graph ของโปรเจกต์ Rust พัฒนาโดยทีมงาน **Embark Studios** ภายใต้สัญญาอนุญาตแบบ Dual-license (`MIT OR Apache-2.0`) 

หน้าที่หลักของมันคือการตั้งด่านตรวจในรูปแบบ Rule-based ซึ่งเราสามารถเลือกเปิด/ปิด และกำหนดระดับความเข้มงวดได้ 3 ระดับ ดังนี้
- `deny` ถือเป็น Error และทำให้การรัน (Build/CI) ล้มเหลวทันที
- `warn` แจ้งเตือนข้อควรระวัง แต่ยังยอมให้ผ่านไปได้
- `allow` อนุญาต ไม่ต้องแจ้งเตือนใด ๆ

## 4 ด่านตรวจหลักของ cargo-deny

เราสามารถสั่งรันตรวจทุกด่านพร้อมกันผ่านคำสั่ง `cargo deny check` หรือจะเลือกตรวจทีละด่านก็ได้

### 1. advisories - ตรวจสอบช่องโหว่ความปลอดภัยที่เคยถูกรายงาน
ด่านนี้จะตรวจหาช่องโหว่ของ crate โดยอ้างอิงจากฐานข้อมูล [RustSec advisory-db](https://github.com/rustsec/advisory-db) (ฐานข้อมูลเดียวกับที่ `cargo audit` ใช้งาน) หาก crate ตัวไหนมีหมายเลข RUSTSEC ID ผูกอยู่ หรือถูกแจ้งเตือนความปลอดภัย จะถูกตรวจจับได้ทันที

```bash
cargo deny check advisories
```

### 2. licenses - ตรวจสอบความถูกต้องของใบอนุญาต (License Compliance)
ด่านนี้ช่วยยืนยันว่า dependency ทุกตัวที่เราใช้งานอยู่ ใช้สัญญาอนุญาตแบบเปิด (Open Source License) ในระดับที่เรายอมรับได้ เช่น MIT หรือ Apache-2.0 โดยกำหนดผ่านรายชื่อมาตรฐาน SPDX และยังตั้งค่า `confidence-threshold` เพื่อตรวจความถูกต้องของเนื้อหาไฟล์ License ได้อีกด้วย

```bash
cargo deny check licenses
```

### 3. bans - แบน Crate ต้องห้าม และตรวจจับเวอร์ชันซ้ำซ้อน
ด่านนี้ทำหน้าที่ 2 อย่าง คือ
1. **บล็อก Crate เป็นรายชื่อ (by name)** ห้ามไม่ให้ใครดึง crate บางตัวเข้ามาในโปรเจกต์เด็ดขาด
2. **ตรวจจับเวอร์ชันซ้ำซ้อน (Duplicate versions)** แจ้งเตือนเมื่อมีการดึง crate เดียวกันแต่คนละเวอร์ชันเข้ามา ซึ่งทำให้ขนาด binary ใหญ่ขึ้นโดยไม่จำเป็น

```bash
cargo deny check bans
```

### 4. sources - ตรวจสอบแหล่งที่มา ต้องมาจากที่ที่เชื่อถือได้เท่านั้น
ด่านนี้ช่วยการันตีว่า dependency ทั้งหมดถูกดาวน์โหลดมาจากแหล่ง (Registry หรือ Git repo) ที่เราอนุญาตไว้เท่านั้น หากมี crate แปลกปลอมที่แอบชี้ไปโหลดจาก private repository อื่น หรือ source ที่ไม่อยู่ใน Allowlist ตัว cargo-deny จะแจ้งเตือนหรือปฏิเสธทันที

```bash
cargo deny check sources
```

## เริ่มต้นใช้งาน

เริ่มต้นใช้งานได้ง่าย ๆ เพียง 3 คำสั่ง

```bash
# 1. ติดตั้งเครื่องมือ
cargo install --locked cargo-deny

# 2. สร้างไฟล์คอนฟิกเริ่มต้น (deny.toml)
cargo deny init

# 3. รันการตรวจสอบทุกด่าน
cargo deny check
```

นอกจากนี้ สำหรับทีมที่ใช้ GitHub Actions ทาง Embark Studios ยังมี Action สำเร็จรูปอย่าง [`cargo-deny-action`](https://github.com/EmbarkStudios/cargo-deny-action) ให้เรียกใช้ใน Pipeline ได้สะดวกมาก

## ตัวอย่างไฟล์ตั้งค่า `deny.toml`

โครงสร้างการตั้งค่าหลัก ๆ จะแบ่งตาม 4 ด่านตรวจ (รวมถึงหมวดเสริมอย่าง `[graph]` และ `[output]`)

```yaml
# ด่าน Advisories ห้ามใช้ Crate ที่ถูกดึงออกจากระบบ (Yanked)
[advisories]
yanked = "deny"
# สามารถเว้นการตรวจบางตัวที่ตรวจสอบแล้วว่าปลอดภัยได้:
# ignore = [ { id = "RUSTSEC-xxxx-xxxx", reason = "เหตุผลที่อนุญาต..." } ]

# ด่าน Licenses อนุญาตเฉพาะ License ที่กำหนด
[licenses]
allow = ["MIT", "Apache-2.0", "BSD-3-Clause"]
confidence-threshold = 0.8

# ด่าน Bans แจ้งเตือนหากพบ crate เวอร์ชันซ้ำซ้อน
[bans]
multiple-versions = "warn"

# ด่าน Sources บล็อก registry และ git ที่ไม่รู้จัก
[sources]
unknown-registry = "deny"
unknown-git = "deny"
allow-git = []
```

*ระดับความเข้มงวดจะเรียงจาก `deny` > `warn` > `allow` ซึ่งสามารถนำไปปรับใช้ได้กับทุกหมวดหมู่*

## กรณีศึกษาสดๆร้อนๆ เมื่อมัลแวร์บุก Supply Chain ของ Rust

เมื่อวันที่ 20 สิงหาคม 2026 ทีม Rust Security Response Team ได้ยืนยันเหตุการณ์มัลแวร์บน crates.io โดยพบ crate ชื่อ `proc-macro1` ซึ่งแอบฝัง build script สำหรับดาวน์โหลด payload อันตรายลงเครื่องของนักพัฒนา 

จากนั้นพบว่า crate อื่น ๆ เช่น `arrayref`, `proc-macro-en`, `aovine`, `internment@0.8.7` และ `append-only-vec@0.1.9` ก็ถูกอัปเดตให้ไปพึ่งพา `proc-macro1` เช่นกัน แม้ทีมงาน crates.io จะทำการลบเวอร์ชันอันตรายและระงับบัญชีผู้โจมตีอย่างรวดเร็ว แต่เหตุการณ์นี้ย้ำเตือนว่าการป้องกันล่วงหน้าคือสิ่งจำเป็น

**ด่านตรวจของ `cargo-deny` ช่วยป้องกันเหตุการณ์แบบนี้ได้อย่างไร?**

- **Advisories** ดักจับได้ทันทีที่มีการออก RUSTSEC ID เตือนภัยในระบบ
- **Bans** สามารถสั่งแบนชื่อ crate แปลกปลอมได้ทันที เช่น ใส่ `deny = ["proc-macro1"]` ไว้ล่วงหน้า
- **Sources** หากมี crate พยายามชี้ไปยัง git หรือ registry แปลกปลอม การตั้ง `unknown-registry = "deny"` จะบล็อกตั้งแต่ยังไม่เริ่มดาวน์โหลด

> **ข้อควรระวัง** ไม่มีเครื่องมือใดที่ป้องกันภัยแบบ Zero-day (เหตุการณ์ที่เพิ่งเกิดและยังไม่มีใครแจ้งเตือน) ได้ 100% พลังที่แท้จริงจึงอยู่ที่กลยุทธ์ **"Defense in Depth" (การป้องกันหลายชั้น)** ทั้งการใช้หลายด่านร่วมกัน การอัปเดตฐานข้อมูลความปลอดภัยสม่ำเสมอ และการตั้งให้เป็น Required Check ใน CI/CD ไม่ให้โค้ดที่มีความเสี่ยงหลุดรอดไปได้

## ตัวอย่างการนำไปใช้จริงในโปรเจกต์

ในโปรเจกต์นี้ (rust-blog นั่นเอง) ผมเปิดใช้งานทั้ง `cargo deny check` และ `cargo audit` เป็น Gate บังคับผ่านใน CI Workflow (`deploy.yml`) โดยมีแนวทางการตั้งค่าใน `deny.toml` ดังนี้ครับ

- **`yanked = "deny"`** - ไม่อนุญาตให้ใช้ crate ที่ถูก yank ออกจาก crates.io เด็ดขาด
- **`licenses.allow`** - อนุญาตเฉพาะใบอนุญาตแบบ Permissive (MIT, Apache-2.0, BSD-3-Clause, ISC, CC0-1.0 ฯลฯ)
- **`sources.unknown-* = "deny"`** - อนุญาตเฉพาะ crates.io และ Git repo ที่ระบุไว้ชัดเจนเท่านั้น
- **`bans.multiple-versions = "warn"`** - แจ้งเตือนเมื่อมี dependency ซ้ำซ้อน เพื่อคอย optimize ขนาดของโปรเจกต์

สำหรับ Advisory บางตัวที่จำเป็นต้องใช้งานชั่วคราว (เช่น เป็นปัญหาเฉพาะ build-time หรือรอ crate ต้นทางอัปเดต) เราจะใส่ไว้ในรายการ `ignore` พร้อมระบุเหตุผลอย่างละเอียดทั้งใน `deny.toml` และ `.cargo/audit.toml` เพื่อให้เข้าใจตรงกันว่าทำไมถึงยอมรับความเสี่ยงดังกล่าว

## สุดท้ายแล้ว

`cargo-deny` ไม่ได้ช่วยให้โค้ดของคุณคอมไพล์เร็วขึ้นหรือกินแรมน้อยลงนะครับ แต่มันช่วยให้ **ทุกอย่างที่คุณนำมาใช้ในโปรเจกต์ โปร่งใส ตรวจสอบได้ และปลอดภัย** 

การนำ `cargo-deny` ไปผสานรวมกับ `cargo audit`, `cargo clippy` และชุดทดสอบอัตโนมัติบน CI/CD คือหนึ่งในวิธีที่ดีที่สุดในการแสดงให้เห็นว่าคุณให้ความสำคัญกับความปลอดภัยของ Supply Chain อย่างจริงจัง

ดังนั้นแล้วเริ่มต้นตั้งค่าโปรเจกต์ของคุณด้วย `cargo deny init` ตั้งแต่วันนี้ ดีกว่าต้องมาตามแก้ปัญหาหลังจากมัลแวร์หลุดเข้าไปในระบบแล้วครับ
