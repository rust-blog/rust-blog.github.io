เรื่องนี้เกิดกับแอปเดสก์ท็อป Tauri ที่ผมพัฒนาอยู่ วันดีคืนดีก็ลองเปิด terminal แล้วรัน `strings` ในไฟล์ release build ของตัวเองดูเล่น ๆ เท่านั้นแหละครับ คีย์สองตัวจากเซอร์วิส logging กับที่เก็บรูปผู้ใช้โผล่ให้เห็นเป็น plain text กันแบบโต้ง ๆ ทั้งที่ repo สะอาดกริบ ไม่มีคีย์หลุดในโค้ดมาเป็นปีแล้ว เพราะผมย้ายไปเก็บใน CI secret เรียบร้อย แถม secret scanner ก็เขียวผ่านฉลุยทุก PR ด้วยนะ

สิ่งที่ทำให้คาใจมากกว่าตัวเหตุการณ์คือ แล้วมันเข้าไปอยู่ในนั้นได้ยังไงกันแน่? ในเมื่อโค้ดที่เขียนใช้ `env!` ซึ่งแค่ชื่อก็บอกอยู่แล้วว่าเกี่ยวกับ "environment" ค่าที่ควรจะดึงมาจากสภาพแวดล้อมภายนอก กลับเข้าไปฝังตัวอยู่ในไฟล์ไบนารีที่เราส่งให้ผู้ใช้ดาวน์โหลดเฉยเลย บทความนี้เรามาดูกันโดยละเอียดครับ โดยผมจะใช้ `cargo expand` คลี่โค้ดออกมาดูทีละขั้นว่ามันเกิดอะไรขึ้นตั้งแต่ก่อน compile แล้วปิดท้ายด้วยการไปขุดดูไบต์จริง ๆ ข้างในไฟล์ build กัน

## 1. เครื่องมือสแกนที่เก่ง แต่ดันตรวจผิดก็จบ

สาเหตุที่เรื่องแบบนี้เกิดขึ้นซ้ำแล้วซ้ำเล่ากับหลายๆคน เป็นเพราะ workflow ความปลอดภัยที่เราคิดว่ารัดกุมดีแล้ว แท้จริงแล้วมันทำงานอยู่แค่บน "โค้ดที่มนุษย์เขียน" ทั้งนั้น ไม่ว่าจะเป็นการเอา key ออกจาก repo, การผูกค่าไว้ใน CI secret, หรือการตั้ง scanner คอยดักจับ diff ในทุก PR แต่ทันทีที่ค่านั้นไหลผ่าน compiler เข้าไป มันไม่ได้มีสถานะเป็นโค้ดที่นักพัฒนาเขียนอีกต่อไปแล้ว มันกลายเป็นข้อมูลของโปรแกรมไปเรียบร้อย และ scanner ส่วนใหญ่ที่เก่งเรื่องสแกน repo ก็ไม่ได้ถูกออกแบบมาให้แงะไฟล์ไบนารีดูตั้งแต่แรก

ช่องว่างตรงนี้นี่แหละครับที่เป็นจุดตาย และที่สำคัญคือคนที่คิดจะแกะเอาคีย์ ไม่จำเป็นต้องมีสกิล reverse engineering ระดับเทพเลยด้วยซ้ำ แค่คำสั่งพื้นฐานอย่าง `strings` ที่ติดมากับระบบปฏิบัติการแทบทุกเครื่องก็ทำได้แล้ว

## 2. env! แท้จริงแล้วเป็น macro ไม่ใช่คำสั่งอ่านค่าตอนรัน

ถ้าเราไปเปิดดูเอกสารของ `std` ตัว `env!` ถูกระบุไว้ชัดเจนว่า มันจะ "expand to the value of the named environment variable at compile time, yielding an expression of type `&'static str`" ซึ่งหมายความว่า ตัวมันจะถูกแทนที่ด้วย string literal ดิบ ๆ ตั้งแต่โค้ดยังไม่ทันถูกคอมไพล์เป็น machine code เลยด้วยซ้ำ ผลที่ตามมาคือ

ถ้าตอน build ไม่มีตัวแปรนี้อยู่ในระบบ ตัว compiler จะสั่ง error ทันที พร้อมกับแนะนำให้เปลี่ยนไปใช้ `std::env::var` หากต้องการอ่านค่าตอน runtime จริง ๆ และถ้ามีตัวแปร แต่ค่านั้นไม่ใช่ Unicode (UTF-8) ที่ถูกต้อง ก็จะ build ไม่ผ่านเช่นกัน ส่วนฝาแฝดของมันอย่าง `option_env!` จะให้ผลลัพธ์เป็น `Option<&'static str>` แทน โดยจะคืนค่า `None` ออกมาถ้าไม่พบตัวแปร แต่ถ้ามีเมื่อไหร่ มันก็จะฝังค่านั้นลงไปในไฟล์แบบเดียวกับ `env!` เป๊ะ ๆ ไม่ต่างกันเลย

อีกจุดหนึ่งที่หลายคนมักเข้าใจผิดคือ `env!` จะกวาดอ่านทุกอย่างที่อยู่ใน process environment ของ rustc ณ เวลานั้น ซึ่งไม่ได้มีแค่ตัวแปรที่เรา export ใน shell ตอนทดสอบ แต่ยังรวมไปถึง CI secret ที่ถูกผูกเป็น env variable ในขั้นตอน build, ตัวแปรที่ build script พ่นออกมาผ่าน `cargo::rustc-env=KEY=value` (หรือซินแทกซ์เดิมคือ `cargo:rustc-env` แบบ colon เดี่ยว) รวมถึงค่าเก่าที่อาจจะค้างอยู่ในเครื่องตั้งแต่ตอนนั่งแก้บั๊ก ซึ่งข้อสุดท้ายนี้แหละที่เจ็บแสบที่สุด เพราะมักไม่มีใครจำได้ว่าตัวเองเผลอไปเซ็ตไว้ตั้งแต่เมื่อไหร่

ดังนั้นชะตากรรมของตัวแปรจึงถูกชี้ขาดตั้งแต่กระบวนการแรก ๆ ของการ build ถ้าเราอยากให้ค่าถูกดึงมาจากข้างนอกจริง ๆ ในตอนที่นำแอปไปใช้งาน แนวทางที่ถูกต้องคือต้องอ่านค่าตอน runtime ผ่าน `std::env::var` หรือใช้ระบบ secrets management เข้ามาจัดการ ซึ่งเราจะพูดถึงในท้ายบทความครับ

## 3. ลองให้ cargo expand แงะโค้ดให้เห็นกันจะ ๆ

ผมลองสร้าง crate จำลองเล็ก ๆ ขึ้นมาชื่อ `env_demo` เพื่อจำลองสถานการณ์จริงให้เห็นภาพ คีย์ตัวแรกเป็นคีย์บังคับ ส่วนอีกตัวเป็นแบบ optional

```rust
// Key 1: คีย์ logging service จำเป็นต้องมีตอน compile
const LOG_API_KEY: &str = env!("LOG_API_KEY");

// Key 2: คีย์ photo storage เป็น optional ตอน compile
const STORAGE_API_KEY: &str = match option_env!("STORAGE_API_KEY") {
    Some(key) => key,
    None => "none",
};

fn main() {
    let mode = std::env::args().nth(1).unwrap_or_default();
    if mode == "dump" {
        println!("{LOG_API_KEY}");
        println!("{STORAGE_API_KEY}");
    } else {
        println!("run with `dump` to print the configured keys");
    }
}
```

โดยผมเซ็ตค่าสมมติขึ้นมาทดสอบดังนี้ครับ

```sh
export LOG_API_KEY="sk-live-DEMO-1234567890abcdef"
export STORAGE_API_KEY="ak-storage-DEMO-fedcba0987654321"
```

เราจะใช้ `cargo expand` ซึ่งเป็น tool ยอดนิยมของคุณ dtolnay ที่เอาคำสั่งภายในของ compiler อย่าง (`cargo rustc --profile=check -- -Zunpretty=expanded`) มาครอบ แล้วจัดฟอร์แมตให้อ่านง่ายด้วย rustfmt ปัจจุบันตัวนี้สามารถรันบน Rust stable ได้เลย ติดตั้งง่าย ๆ ด้วยคำสั่ง `cargo install cargo-expand`

```sh
cargo expand
```

และนี่คือผลลัพธ์ที่ได้ออกมาจริงจากเครื่องของผม (ตัดโค้ด boilerplate ส่วน `fn main` ที่ไม่เกี่ยวข้องออกไปเพื่อให้ดูง่ายขึ้น)

```rust
#![feature(prelude_import)]
extern crate std;
#[prelude_import]
use std::prelude::rust_2024::*;
const LOG_API_KEY: &str = "sk-live-DEMO-1234567890abcdef";
const STORAGE_API_KEY: &str = match ::core::option::Option::Some(
    "ak-storage-DEMO-fedcba0987654321",
) {
    Some(key) => key,
    None => "none",
};
```

พอมองดูบรรทัดตรงกลาง จะเห็นได้ชัดเลยว่าไม่มีคำว่า `env!` หรือ `option_env!` ปรากฏอยู่แม้แต่คำเดียว มันถูกแทนที่ด้วย string literal ลงไปในโค้ดดิบ ๆ ตรงนั้นเรียบร้อยแล้ว (ฝั่ง `option_env!` ถูกแปลงกลายเป็น `Option::Some(...)` สำเร็จรูปไปเลย เพราะ compiler รู้ค่าล่วงหน้าตั้งแต่ตอนนั้นแล้ว) นี่คือหลักฐานชัดเจนว่าคำว่า "compile time" ทำงานอย่างไร เพราะข้อมูลจริงถูกนำมาฝังลงในโค้ดตั้งแต่ก่อนจะเริ่มขั้นตอน type check เสียอีก

## 4. ตามไปขุดดูในไฟล์ไบนารี

ทีนี้ลอง build แบบ release แล้วลองสวมบทบาทเป็นคนทั่วไปที่ไม่ได้มีเครื่องมือ reverse engineering อะไรเลย มีแค่คำสั่ง `strings` ตัวเดียว

```sh
cargo build --release
strings target/release/env_demo | grep DEMO
```

```text
sk-live-DEMO-1234567890abcdef
ak-storage-DEMO-fedcba0987654321
```

ปรากฏว่าเจอครบทั้งสองคีย์แบบไม่มีตกหล่น ขนาดตัวหลังถูกเขียนผ่าน `option_env!` และผ่านการ optimize ขั้นสุดของ release mode มาแล้วก็ตาม สาเหตุเป็นเพราะพฤติกรรมพื้นฐานของ `&'static str` นั่นเองครับ เมื่อมันเป็น literal มันจะต้องอยู่รอดและถูกอ่านได้ตลอดช่วงชีวิตของโปรแกรม ทำให้มันถูกจัดวางไว้ใน read-only data section ของไฟล์ (บน Windows/MSVC คือ `.rdata` ส่วนบน Linux/macOS คือ `.rodata`) ข้อมูลที่อยู่ใน section นี้คือตัวอักษรเรียงต่อกันเป็นไบต์ดิบ ๆ ไม่ได้มีการเข้ารหัสหรือซ่อนอะไรเลย ต่อให้เราสั่ง `strip` ตัว binary ก็ไม่ช่วยอะไร เพราะมันทำหน้าที่แค่ลบ symbol table กับ debug info ออก แต่ไม่ได้ไปยุ่งกับ data section เลยแม้แต่น้อย ส่วน LTO (Link-Time Optimization) หรือตัว optimizer ต่าง ๆ ก็ไม่ได้มีหน้าที่ซ่อนข้อมูล มีแต่จะรวมหรือจัดระเบียบตำแหน่งให้มันแค่นั้น

> ⚠️ เกร็ดเล็ก ๆ จากการทดลองรอบแรกที่น่าสนใจ ตอนแรกผมเขียน `main` แบบง่ายเกินไป คือเอาค่ามาแค่เช็คความยาว `LOG_API_KEY.len()` กับเอาไปเปรียบเทียบ `STORAGE_API_KEY != "none"` ปรากฏว่าพอ release build ออกมา **ใช้คำสั่ง strings หาคีย์ไม่เจอเลยสักตัว** เพราะ compiler มันฉลาดพอที่จะทำ constant-folding ประเมินผลลัพธ์เป็นค่าคงที่ไปตั้งแต่ตอน compile ทำให้ตัวแปร literal นั้นกลายเป็น dead code และถูกตัดทิ้งออกไปหมด ตอนนั้นผมเกือบจะเข้าใจผิดแล้วว่ามันไม่ฝัง แต่พอกลับมาแก้โค้ดให้มีการ print หรือนำไปเรียก HTTP client ใช้งานจริง ๆ คีย์ก็กลับมาโผล่ครบทั้งคู่ทันที เพราะฉะนั้น อย่าไปหวังพึ่งพา optimization ให้ช่วยปกปิดความลับเด็ดขาดครับ มันจะลบทิ้งแค่สิ่งที่เราไม่ได้ใช้เท่านั้น แต่ในโปรแกรมจริง สิ่งที่เราต้องการใช้งาน มันจะถูกเก็บไว้เสมอ

และถ้าเป็นฝั่งเว็บที่คอมไพล์ไปเป็น WebAssembly (WASM) ก็ไม่รอดเหมือนกันครับ เพราะไฟล์ `.wasm` เองก็เก็บ string literal เอาไว้ใน data segment เช่นกัน ถ้าเราเอา `strings` ไปส่องไฟล์ `.wasm` ก็จะได้ผลลัพธ์แบบเดียวกันเป๊ะ ตัวอย่างที่เห็นภาพง่าย ๆ คือบล็อกหน้านี้ที่คุณกำลังอ่านอยู่ ตัวเว็บมีการฝังเนื้อหาโพสต์ทั้งหมดไว้ตั้งแต่ตอน compile ผ่าน macro `include_dir!` ซึ่งกรณีนี้ปลอดภัยร้อยเปอร์เซ็นต์ เพราะเนื้อหาในบล็อกเป็นข้อมูลสาธารณะ ปัญหามันไม่ได้อยู่ที่กระบวนการฝังข้อมูลตอน compile แต่อยู่ที่ว่าสิ่งที่เราเลือกฝังลงไปนั้น ดันเป็น "ความลับ" ต่างหาก

## 5. ถ้าลืมใส่ตัวแปรไว้ตอน build จะเกิดอะไรขึ้น?

สำหรับ macro `env!` พฤติกรรมของมันถือว่าแฟร์และตรงไปตรงมามาก เพราะถ้าไม่มีตัวแปร มันจะสั่ง compile error ทันทีพร้อมแจ้งข้อความที่ชัดเจน ผมลองลบค่าตัวแปรออกแล้วสั่ง `cargo check`

```text
error: environment variable `LOG_API_KEY` not defined at compile time
 --> src\main.rs:2:27
  |
2 | const LOG_API_KEY: &str = env!("LOG_API_KEY");
  |                           ^^^^^^^^^^^^^^^^^^^
  |
  = help: use `std::env::var("LOG_API_KEY")` to read the variable at run time
```

ข้อดีคือ ถ้าเราลืมตั้งค่าใน CI pipeline มันจะพังให้เห็นทันที แต่สิ่งที่ต้องระวังให้จงหนักคือ มันจะร้องเตือนเฉพาะเคส "ไม่มีค่า" เท่านั้น แต่ในกรณี "มีค่าอยู่แล้ว และค่านั้นหลุดเข้าไปนอนรออยู่ในไบนารีเรียบร้อย" ตัว compiler จะไม่บ่นหรือเตือนอะไรคุณเลยแม้แต่คำเดียว

และตัวที่แอบน่ากลัวยิ่งกว่าคือ `option_env!` เพราะเมื่อมันหาตัวแปรไม่เจอ มันจะเงียบกริบแล้วส่งค่า `None` คืนมาให้โค้ดเดินหน้าต่อด้วย fallback value ที่เราดักไว้ บั๊กประเภท "คีย์ไม่ถูกฝังลงไป" กับ "คีย์เผลอฝังลงไปแล้ว" จึงสามารถรันผ่านชุดโค้ดเดียวกันไปได้อย่างแนบเนียน

## 6. แล้วถ้าเราเข้ารหัส (Encrypt) หรือทำ Obfuscation ล่ะ?

คำถามนี้มักจะตามมาเสมอเวลาคุยกันเรื่องนี้ คำตอบแบบไม่อ้อมค้อมคือ มันช่วยเพิ่มความยุ่งยากให้คนแกะได้จริง แต่มันไม่ใช่ "การแก้ปัญหาเชิงความปลอดภัย" เลยแม้แต่น้อย ลองนึกภาพตามง่าย ๆ ครับ ถ้าเราเก็บคีย์แบบที่เข้ารหัสไว้ในไฟล์ไบนารี ตอนที่โปรแกรมจะนำไปใช้งานจริง ๆ มันก็ต้องถอดรหัสออกมาใช้อยู่ดี แปลว่ากุญแจสำหรับถอดรหัส มันก็ต้องวางแอบอยู่ที่ไหนสักแห่งในไฟล์ไบนารีนั้นด้วย หรือถ้าคุณบอกว่าจะให้ไบนารีไปดึงกุญแจมาจากข้างนอก... อ้าว ถ้าระบบสามารถดึงข้อมูลจากข้างนอกได้ปลอดภัยอยู่แล้ว สู้ไปดึงตัว API key ตัวจริงมาจากที่นั่นตรง ๆ แต่แรกเลยไม่ดีกว่าหรือ? สรุปสั้น ๆ คือ ตราบใดที่โปรแกรมสามารถนำข้อมูลนั้นมาใช้งานได้เองโดยไม่ต้องรอการป้อนค่าจากผู้ใช้ ใครก็ตามที่มีไฟล์นั้นอยู่ในมือย่อมสามารถแกะมันออกมาได้เสมอ ไม่แกะจากตัวไฟล์ ก็ไปดักเอาจาก RAM ตอนโปรแกรมกำลังรัน

แนวทางที่ช่วยป้องกันได้จริง ๆ จึงไม่ใช่การพยายาม "ซ่อน" แต่เป็นการ "ย้ายความลับออกไป" ให้พ้นจากตัวไฟล์ โดยไปผูกไว้กับผู้ใช้งานหรือบริบทของเครื่องแทน เช่น การใช้ token ที่หมดอายุตาม session, การเก็บ credential ไว้ใน Secure Enclave / OS Keychain ที่ต้องอาศัยการยืนยันตัวตนของผู้ใช้, หรือการให้ client คุยผ่าน backend ของเราเองแล้วให้ backend เป็นตัวถือ secret key ทั้งหมดนี้คือการออกแบบเพื่อไม่ให้มี secret key อยู่ในแอปตั้งแต่แรก

สำหรับมิติด้านความปลอดภัยบนหน่วยความจำ ผมเคยลงรายละเอียดไว้อย่างลึกในบทความ [ล้างรหัสผ่านผิดก้อน: เมื่อ zeroize ไม่เคยแตะข้อมูลตัวจริง](/post/zeroize-wrong-allocation) ใครสนใจอยากเห็นภาพว่า เวลามีความลับค้างอยู่ใน RAM แล้วมันถูกล้างออกจริงไหม หรือค้างอยู่อย่างไร แนะนำให้อ่านต่อได้เลยครับ

## 7. ตั้งการสแกนไฟล์ไบนารีบน CI

หลังจากเจอเหตุการณ์นั้น สิ่งแรกที่เราสามารถนำมาปรับใช้แบบด่วน ๆ คือการเพิ่มขั้นตอนสุดท้ายใน CI pipeline เพื่อสแกน artifact ที่กำลังจะถูกปล่อยออกไปเป็น release build จริง

```yaml
- name: Scan the release binary for key material
  run: |
    if strings target/release/app | grep -E '(sk_live_|AKIA[0-9A-Z]{16}|ghp_[A-Za-z0-9]{36}|-----BEGIN)'; then
      echo "::error::possible secret embedded in the binary"
      exit 1
    fi
```

แต่เราต้องรู้เท่าทันข้อจำกัดของวิธีนี้ด้วยเช่นกัน สคริปต์นี้ตรวจจับได้เฉพาะ secret ที่หลุดมาเป็น plain text และมีแพทเทิร์นตรงกับ regular expression ที่เรากำหนดไว้เท่านั้น ถ้ามีการ obfuscate ค่ามา หรือถ้าเราเขียน regex กว้างเกินไป เช่น สแกนหาคำว่า `api_key` ดื้อ ๆ มันก็มักจะไปเจอกับ false positive อย่างชื่อตัวแปรหรือ error message ของ dependency แทน ทางที่ดีคือควรกำหนด prefix เฉพาะของบริการที่เราใช้งานจริง ๆ เป็นหลัก และจำไว้เสมอว่า การสแกนนี้ทำได้แค่ "ป้องกันสำหรับอนาคต" เท่านั้น ส่วนคีย์ไหนที่สงสัยว่าเคยหลุดออกไปแล้ว สิ่งเดียวที่ต้องทำทันทีคือการ rotate (เปลี่ยนคีย์ใหม่) และ revoke (ยกเลิกคีย์เดิม) ทิ้งซะ

ส่วนใครที่สนใจเรื่องการแกะดูโครงสร้างภายในไฟล์ binary รวมถึงวิธีลดขนาดไฟล์ ผมเคยเขียนสรุปไว้ใน [บทความนี้](/post/med-recon-binary-size) แวะไปอ่านกันต่อได้ครับ

## 8. สรุปแล้ว แนวทางที่ถูกต้องควรทำอย่างไร?

วิธีจัดการขึ้นอยู่กับว่า โค้ดชุดนั้นถูกนำไปรันอยู่ที่ไหน ซึ่งผมสรุปเป็นตารางให้เข้าใจง่าย ๆ ดังนี้ครับ

| บริบทการใช้งาน | ฝังคีย์ในโค้ดได้ไหม? | แนวทางที่ถูกต้อง |
| --- | --- | --- |
| Static Web / WASM (เช่น [CodeFrame](https://github.com/suradet-ps/codeframe)) | **ห้ามเด็ดขาด** อะไรก็ตามที่ส่งถึงเบราว์เซอร์ ให้ถือว่ารั่วไหลสู่สาธารณะแล้ว | ต้องย้าย logic ที่เรียก service ไปไว้ที่ backend ฝั่ง client ต้องไม่มีสิทธิ์ถือ master key ใด ๆ |
| แอปเดสก์ท็อป (Tauri, GUI ทั่วไป) | **ห้ามเด็ดขาด** เพราะไฟล์ที่แจกให้ดาวน์โหลด ถือเป็นของสาธารณะ | ให้ผู้ใช้ล็อกอินเพื่อดึง token ส่วนตัวมาเก็บไว้ใน OS Keychain หรือยิง request ผ่าน backend ของเรา เพื่อให้ backend เป็นคนถือคีย์จริง (สุดท้ายผมก็เลือกวิธีนี้ โดยให้แอปอัปโหลดไฟล์ผ่าน backend ตัวกลางของเราแทน) |
| CLI ที่แจกจ่ายให้คนอื่นใช้ | **ห้ามเด็ดขาด** ด้วยเหตุผลเดียวกับแอปเดสก์ท็อป | ออกแบบให้รับ token ผ่าน flag หรืออ่านจาก config file ในเครื่องผู้ใช้ |
| Backend ของเราเอง | ทำได้ แต่**ไม่แนะนำ** | ให้อ่านค่าตอน runtime จาก environment variable ที่ถูก inject มาจาก Secret Manager หรือเปลี่ยนไปใช้ Workload Identity / IAM Role แทนการแปะ static key |
| ค่าทั่วไปที่ไม่เป็นความลับ (เวอร์ชัน, feature flag, public URL) | **ทำได้เต็มที่** | ใช้ `env!` ตอบโจทย์และเหมาะกับงานแบบนี้ที่สุด |

เพื่อไม่ให้บทความนี้จบไปเฉย ๆ ผมขอฝาก Checklist สั้น ๆ เอาไว้ให้ทุกคนลองนำไป audit ตรวจสอบโปรเจกต์ของตัวเองกันดูครับ

* ลองใช้ฟีเจอร์ search ใน editor ค้นหาคำว่า `env!(`, `option_env!(`, `cargo::rustc-env` และ `cargo:rustc-env` ทั่วทั้ง workspace แล้วตั้งคำถามกับทุกจุดว่า ค่านี้ถือเป็นความลับหรือไม่? ถ้าใช่ ให้รีบเปลี่ยนไปอ่านค่าตอน runtime แทนทันที
* ตรวจสอบดูว่า มี CI secret ตัวไหนบ้างที่ถูก map เข้าไปเป็น environment variable ในขั้นตอน build ของ CI เพราะค่านั้นมีสิทธิ์สูงมากที่จะถูก compile ฝังติดไปกับ artifact
* ถ้ากำลังพัฒนาแอปเดสก์ท็อป ให้วาง architecture ให้ชัดเจนตั้งแต่ Day 1 ว่า คีย์ของระบบภายนอกจะไปอยู่ที่ไหน และ credential ของผู้ใช้จะถูกเก็บรักษาอย่างไร อย่าใช้ข้ออ้างว่า "ยังไม่มี backend เอาไว้ต่อ ค่อยทำ ฝังคีย์ไปก่อนแล้วกัน" เพราะกว่าจะรู้ตัวอีกที คีย์นั้นอาจจะกระจายไปอยู่ในเครื่องของผู้ใช้งานทุกคนแล้ว
* ลองทดสอบด้วยตัวเองตอนนี้เลยครับ รันคำสั่ง `strings target/release/<ชื่อไบนารีของคุณ> | grep -i -E "key|token|secret"` ดู ถ้าเกิดเจออะไรโผล่ขึ้นมา อย่างน้อยตอนนี้คุณก็รู้แล้วว่ามันแอบหลุดไปฝังตัวอยู่ตรงจุดไหน

บทความนี้เริ่มต้นจากความสงสัยว่า จริง ๆ แล้ว `env!` ทำงานอย่างไรกับโค้ดของเรากันแน่ และคำตอบของมันก็ชัดเจนและตรงไปตรงมากว่าที่คิด มันไม่เคยดึงค่าตอน runtime เลย แต่มันแทนที่ตัวเองด้วย string literal ค่าจริงลงไปในโค้ด แล้วฝังติดไปกับทุก artifact ที่ถูกสร้างขึ้นมาใน environment นั้น เครื่องมืออย่าง `cargo expand` ช่วยให้เราเห็นกระบวนการนี้ได้ตั้งแต่เนิ่น ๆ และคำสั่งอย่าง `strings` ก็ช่วยสะท้อนผลลัพธ์ปลายทางให้เราเห็นความจริง ซึ่งทั้งสองอย่างนี้เป็นเครื่องมือฟรีที่มีพร้อมให้เราใช้ได้ทันทีในเครื่อง

ประโยคที่ว่า "ย้าย secret ออกจาก repo แล้วก็ปลอดภัยหายห่วง" เป็นสิ่งที่ไม่จริงเสมอไปครับ เพราะตัว source code กับตัวไบนารีมันคือคนละสิ่งกัน และ security scanner ทั่วไปก็คอยดูอยู่แค่หน้าบ้าน สิ่งที่เป็นความลับ ต้องไม่ถูกแปลงเป็นค่าคงที่ในขั้นตอนคอมไพล์ ไม่ว่าจะด้วยวิธีใดก็ตามครับ
