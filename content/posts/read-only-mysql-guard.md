มีโจทย์ข้อหนึ่งที่ตอนแรกที่ผมคิดว่าง่าย แต่พอลงมือออกแบบจริงกลับสนุกและท้าทายกว่าที่คิด นั่นคือ **"โปรแกรมนี้ห้ามแก้ไขข้อมูลในฐานข้อมูลเด็ดขาด"** 

เมื่อฟังดูเผิน ๆ เหมือนแค่สร้าง User ใน MySQL ให้เป็น Read-only ก็น่าจะจบนะ แต่ในความเป็นจริง ฐานข้อมูลที่เรากำลังแตะต้องอยู่นี้คือตาราง `drugitems` ซึ่งเป็น Drug Master (ข้อมูลรายการยาหลัก) ของโรงพยาบาล ระบบอื่น ๆ ทั้งโรงพยาบาลต้องอ่านข้อมูลจากตารางนี้ไปใช้จ่ายยา หากมีข้อมูลแถวใดแถวหนึ่งถูกเขียนทับหรือแก้ไขผิดพลาด ผลลัพธ์ไม่ได้จบแค่มี Error บันทึกใน Log แต่มันกระทบถึงความปลอดภัยของผู้ป่วยโดยตรง

บทความนี้ผมเขียนจึงขึ้นเพื่อถอดบทเรียนจากโปรเจกต์ **DrugItems** ([github.com/suradet-ps/drugitems](https://github.com/suradet-ps/drugitems)) ซึ่งเป็น Desktop Program ที่ใช้ตรวจสอบว่าข้อมูลยาในฐานข้อมูลปัจจุบัน ยังตรงกับไฟล์ Excel Snapshot ที่ผมเคย export ไว้หรือไม่ ปรัชญาของตัวโปรแกรมชัดเจนมาก **Snapshot คือความจริง ส่วนฐานข้อมูลคือผู้ต้องสงสัย** เอากันงี้เลย โปรแกรมมีหน้าที่เพียงแค่ **"รายงานความต่าง"** ไม่ได้มีหน้าที่ **"ซ่อมแซมข้อมูล"** เพราะเดี๋ยวเราจะกลับเข้าไปดูเอง

คำว่าอ่านอย่างเดียว หากเขียนไว้แค่ในเอกสารก็เป็นเพียงคำสัญญาปากเปล่า แต่ในโปรเจกต์นี้ เราบังคับใช้กฎนี้อย่างเข้มงวดผ่านการป้องกันถึง **3 ชั้น (3 Layers)** และนี่คือบันทึกเบื้องหลังการออกแบบ พร้อมโค้ดภาษา Rust จริงจากตัวโปรเจกต์ครับ มาเรียนรู้ไปด้วยกันครับ

## 1. ทำไมแค่สัญญาด้วยเอกสาร ถึงไม่เคยพอ

ความเสี่ยงที่ข้อมูลในตารางยาจะเสียหาย ไม่ได้เกิดจากการถูกเจาะระบบ (Hacking) เสมอไป บ่อยครั้งมันเกิดจากความผิดพลาดของทีมนักพัฒนาเอง

- วันนี้เราเขียนโค้ดด้วย `SELECT` แต่วันข้างหน้าอาจมีใครสักคน refactor โค้ดโดยไม่มี peer review แล้วเผลอเปลี่ยนเป็น `UPDATE`
- ในอนาคตอาจมีคนแอบเพิ่มฟีเจอร์ กดปุ่มเดียวเพื่อแก้อัตโนมัติ หลุดเข้ามาโดยไม่ได้ตั้งใจ
- Credential ที่ตั้งใจให้ใช้อ่านอย่างเดียว อาจถูกหยิบไปใช้ผิดงานในโปรเจกต์อื่น
- การประกอบ String เป็น SQL เองโดยขาดความระมัดระวัง จนเกิดช่องโหว่ SQL Injection

หลักการที่เราเลือกใช้คือ **Defense in Depth** (การป้องกันแบบลึกหลายชั้น) โดยตั้งด่านตรวจดักจับความผิดพลาดในแต่ละช่วงเวลาที่ต่างกัน ทุกด่านไม่จำเป็นต้องสมบูรณ์แบบไร้ที่ติ แต่ต้องยึดหลัก **Fail-closed**: *หากตรวจแล้วไม่แน่ใจหรือไม่ชัดเจน ให้ปฏิเสธ (Reject) ไว้ก่อนเสมอ*

## 2. ภาพรวมการป้องกัน 3 ชั้น

| ชั้น | กลไกหลัก | ป้องกันความผิดพลาดประเภทใด | ตำแหน่งในโค้ด |
|---|---|---|---|
| **1** | บัญชี MySQL แบบ Read-only (Least Privilege) | ป้องกันคำสั่งเขียนที่อาจหลุดจากโค้ดไปยัง Database Server | สิทธิ์ระดับฐานข้อมูล (MySQL Server) |
| **2** | Allow-list Keyword Guard | ดักจับกรณีผู้พัฒนาเผลอเขียนคำสั่งที่ไม่ใช่การอ่านลงในโค้ด | `crates/drugitems-db/src/readonly.rs` |
| **3** | ไม่เปิดรับ SQL จากผู้ใช้ + Quote Identifier + Bind Parameter | ป้องกัน SQL Injection และการแทรกโค้ดผ่านชื่อตาราง/คอลัมน์ | `crates/drugitems-db/src/client.rs` |

ในไฟล์เอกสารประกอบของ crate `drugitems-db` ได้ระบุไว้ชัดเจนว่า

> Read-only is enforced twice: the recommended database role is read-only, and every statement is checked by the keyword guard in `readonly` before execution.

หัวใจของเรื่องนี้คือ **"เราบังคับด้วยโค้ด ไม่ใช่แค่บอกให้ทำตามเอกสาร"** ฝั่ง System Admin อาจเป็นผู้จัดการชั้นที่ 1 แต่ชั้นที่ 2 และ 3 ตัวโปรแกรมจะควบคุมความปลอดภัยด้วยตัวเองตั้งแต่ก่อนส่งคำสั่งออกไป

## 3. ชั้นที่ 1 บัญชี MySQL แบบ Read-only

ชั้นนี้ทำงานอยู่บนเซิร์ฟเวอร์ MySQL และเป็นด่านสุดท้ายก่อนที่คำสั่งจะเข้าถึงข้อมูลจริง ถือเป็นด่านที่ปลอดภัยและแข็งแกร่งที่สุด หลักการสำคัญคือ **Least Privilege** กำหนดสิทธิ์ให้เท่าที่จำเป็นต่อการอ่านเท่านั้น และตัดสิทธิ์ในการแก้ไขโครงสร้างหรือการเขียนไฟล์ลงระบบเซิร์ฟเวอร์ทิ้งทั้งหมด

```sql
-- สร้างบัญชีเฉพาะสำหรับโปรแกรมนี้ และจำกัดให้เชื่อมต่อได้เฉพาะเครือข่ายภายในโรงพยาบาล
CREATE USER 'drugitems_ro'@'10.0.0.%' IDENTIFIED BY 'strong-password';

-- ให้สิทธิ์เฉพาะ SELECT และ SHOW VIEW (คำสั่ง SHOW/DESCRIBE/EXPLAIN จะอิงสิทธิ์ SELECT เป็นหลัก)
GRANT SELECT, SHOW VIEW ON hos.* TO 'drugitems_ro'@'10.0.0.%';
FLUSH PRIVILEGES;
```

ในโค้ด Rust ของ DrugItems แม้แต่คอมเมนต์ในเอกสารของ Struct Config ก็เตือนเรื่องนี้ไว้ชัดเจน (`crates/drugitems-db/src/config.rs:14`)

```rust
/// Database user - recommended: a read-only role.
pub user: String,
```

รวมถึงข้อความช่วยเหลือหน้าบ้าน (UI) ก็มีคำแนะนำแจ้งเตือนผู้ใช้งานโดยตรง

> "ตั้งค่าการเชื่อมต่อ MySQL (แนะนำบัญชีที่อ่านได้อย่างเดียว) แล้วกด ทดสอบ"

**ข้อควรระวังสำคัญ** บัญชีนี้ **ต้องไม่ได้สิทธิ์ `FILE` โดยเด็ดขาด** เพราะคำสั่งอย่าง `SELECT ... INTO OUTFILE` แม้จะขึ้นต้นด้วย `SELECT` แต่หากมีสิทธิ์ `FILE` ตัวฐานข้อมูลจะยอมเขียนไฟล์ลงในดิสก์ของเซิร์ฟเวอร์ได้ทันที

## 4. ชั้นที่ 2: Allow-list Keyword Guard

นี่คือกลไกที่เรียบง่ายแต่มีประสิทธิภาพสูงมาก มันเป็นโค้ดขนาดสั้น ๆ เพียง 30 กว่าบรรทัด แต่ทำหน้าที่เป็นด่านคัดกรอง **ทุกคำสั่ง SQL** ก่อนจะถูกส่งไปที่ฐานข้อมูล

`crates/drugitems-db/src/readonly.rs`

```rust
/// SQL keywords allowed to reach a read-only connection.
const ALLOWED_KEYWORDS: [&str; 4] = ["select", "show", "describe", "explain"];

/// Validate that a statement is read-only.
///
/// Intentionally strict: the statement must *begin* with one of the allowed
/// keywords. Anything else (including `WITH`, which can wrap DML) is
/// rejected.
pub fn assert_read_only(stmt: &str) -> Result<()> {
    let first = stmt
        .split_whitespace()
        .next()
        .map(str::to_lowercase)
        .unwrap_or_default();
    if ALLOWED_KEYWORDS.contains(&first.as_str()) {
        Ok(())
    } else {
        Err(Error::ReadOnlyViolation(
            stmt.trim().chars().take(64).collect(),
        ))
    }
}
```

เบื้องหลังการออกแบบโค้ดแต่ละบรรทัดมีเหตุผลรองรับดังนี้

- **ใช้ `.split_whitespace().next()`** ช่วยตัดช่องว่างนำหน้า (Leading Spaces) รวมถึงอักขระ Newline ให้อัตโนมัติ คำสั่งที่มีเคาะวรรคข้างหน้า เช่น `"  select icode from ..."` จึงทำงานได้ถูกต้องโดยไม่ต้องเขียน regex หรือฟังก์ชัน trim ให้ยุ่งยาก
- **แปลงด้วย `.to_lowercase()`** ไวยากรณ์ของ SQL ไม่สนใจตัวพิมพ์เล็ก-ใหญ่ ไม่ว่าจะเป็น `Select`, `SELECT` หรือ `select` จะต้องถูกจัดการให้เทียบเท่ากันทั้งหมด
- **เทียบด้วย Allow-list (White-list) เท่านั้น** การใช้ Block-list (การดักแบนคำอย่าง `INSERT`, `UPDATE`, `DELETE`, `DROP`) แทบไม่มีทางสมบูรณ์ เพราะคำสั่ง SQL มีความซับซ้อนและมีคำสั่งประเภทอื่นอีกมาก การระบุเฉพาะคำที่ **อนุญาตอย่างชัดเจน** จึงปลอดภัยกว่าตามแนวคิด Fail-closed
- **ใช้ `unwrap_or_default()`** กรณีส่ง String ว่างเข้ามา ตัวแรกที่ได้จะเป็น `""` ซึ่งไม่ตรงกับคีย์เวิร์ดใด ๆ และจะถูกปฏิเสธทันทีโดยไม่ต้องเขียนดัก `if` เพิ่มเติม
- **ตัดข้อความด้วย `.take(64)` เมื่อเกิด Error** คำสั่ง SQL มักมีความยาว การเก็บประโยคทั้งหมดลงใน Error Message หรือ Log ไม่ก่อให้เกิดประโยชน์และเปลืองหน่วยความจำ การตัดมาเฉพาะ 64 ตัวอักษรแรกก็เพียงพอที่จะช่วยตรวจสอบตอน Debug ได้แล้ว

### ทำไมต้องปฏิเสธคำสั่ง `WITH`?

หลายคนเข้าใจว่า `WITH` มีไว้ใช้เขียน CTE (Common Table Expression) สำหรับคำนวณหรือเตรียมข้อมูลในการอ่านเท่านั้น แต่ในความเป็นจริง ตั้งแต่ MySQL 8.0 เป็นต้นไป ไวยากรณ์อนุญาตให้นำ `WITH` มาประกบหน้าคำสั่ง `DELETE` หรือ `UPDATE` ได้ด้วย เช่น

```sql
WITH cte AS (SELECT 1) DELETE FROM drugitems
```

คำสั่งนี้ **ถูกต้องตามหลักไวยากรณ์ของ MySQL ทุกประการ** และขึ้นต้นด้วยคำว่า `WITH` หากเราใช้ระบบแบบ Block-list ที่คอยตรวจคำแรก คำสั่งนี้จะหลุดเข้าไปแก้ไขข้อมูลได้ทันที การเลือกใช้ Allow-list ที่จำกัดแค่ 4 คีย์เวิร์ดจึงสามารถปิดช่องโหว่ประเภทนี้ได้ทั้งหมด

### ทดสอบได้ง่าย ๆ โดยไม่ต้องจำลองฐานข้อมูลจริง

เนื่องจาก `assert_read_only` ถูกเขียนเป็น **Pure Function** (รับค่าข้อความ `&str` เข้ามา แล้วส่งผลลัพธ์ `Result` กลับไป โดยไม่มี Side Effect อื่น) เราจึงสามารถเขียน Unit Test ครอบคลุมทุกกรณีได้อย่างรวดเร็ว โดยไม่จำเป็นต้องรัน MySQL ขึ้นมาทดสอบเลย

`crates/drugitems-db/src/readonly.rs`

```rust
#[test]
fn allows_select_statements() {
    assert!(assert_read_only("SELECT * FROM drugitems").is_ok());
    assert!(assert_read_only("  select icode from drugitems").is_ok());
    assert!(assert_read_only("SHOW TABLES").is_ok());
    assert!(assert_read_only("DESCRIBE drugitems").is_ok());
}

#[test]
fn rejects_all_dml_and_ddl() {
    for stmt in [
        "INSERT INTO drugitems (icode) VALUES ('x')",
        "UPDATE drugitems SET name = 'x'",
        "DELETE FROM drugitems",
        "DROP TABLE drugitems",
        "TRUNCATE TABLE drugitems",
        "WITH cte AS (SELECT 1) DELETE FROM drugitems",
        "",
        "   ",
    ] {
        assert!(assert_read_only(stmt).is_err(), "must reject: {stmt:?}");
    }
}
```

### การประกอบเข้ากับจุดทำงานจริง

ใน `client.rs` มีจุดรวมศูนย์เพียงจุดเดียวที่ทุก Query ต้องวิ่งผ่าน ก่อนจะถูกส่งไปประมวลผลด้วย Driver ของ `sqlx`

```rust
let stmt = format!("SELECT {} FROM {table_q}", exprs.join(", "));
assert_read_only(&stmt)?;
```

และหาก Guard ตัวนี้ตรวจพบคำสั่งที่น่าสงสัย โปรแกรมจะแปลงผลลัพธ์เป็น Error ชนิดพิเศษที่แยกขาดจาก Query Error ทั่วไป เพื่อส่งสัญญาณให้ทีมงานรู้ทันทีว่า **"นี่ไม่ใช่ปัญหาของผู้ใช้หรือฐานข้อมูล แต่เป็น Bug ร้ายแรงในโค้ดของโปรแกรมเอง"**

`apps/drugitems-app/src/commands.rs:114`

```rust
drugitems_db::Error::ReadOnlyViolation(_) => {
    CommandError::new(CommandErrorKind::Guard, "ระบบความปลอดภัยของโปรแกรมปฏิเสธคำสั่งนี้")
}
```

## 5. ชั้นที่ 3 ปิดตายช่องทาง SQL จากภายนอก

ในขณะที่ชั้นที่ 2 ทำหน้าที่ "ตรวจกระเป๋าเดินทาง" คำถามถัดมาคือ: *เราจะเปิดช่องให้มีของแปลกปลอมหลุดเข้ามาในกระเป๋าตั้งแต่แรกไปทำไม?* 

หลายระบบชอบเปิดช่องให้ผู้ใช้เขียนหรือปรับแต่ง SQL เอง แล้วค่อยหาทางกรองทีหลัง แต่ DrugItems เลือกตัดปัญหานี้ตั้งแต่ต้นทาง โดยคำสั่ง SQL ทั้งหมดภายในโปรเจกต์มีเพียง 3 รูปแบบเท่านั้น และไม่มีจุดไหนเลยที่รับคำสั่งดิบจากภายนอก

**1. Smoke Test (Ping)** เป็นคำสั่งแบบ Hard-coded ขนาดสั้นเพียงคำสั่งเดียว

```rust
pub async fn ping(&self) -> Result<()> {
    sqlx::query("SELECT 1").execute(&self.pool).await?;
    Ok(())
}
```

**2. ตรวจสอบโครงสร้าง Schema** แม้ชื่อตารางจะมาจากหน้า Setting ของผู้ใช้ แต่จะถูกส่งเข้าไปในลักษณะของ **Bind Parameter (`?`)** เท่านั้น ไม่ใช่การนำ String มาต่อกันตรง ๆ

`crates/drugitems-db/src/client.rs:63`

```rust
const SCHEMA_SQL: &str = "SELECT COLUMN_NAME, DATA_TYPE FROM information_schema.COLUMNS WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = ? ORDER BY ORDINAL_POSITION";
let rows = sqlx::query(SCHEMA_SQL)
    .bind(table)
    .fetch_all(&self.pool)
    .await?;
```

**3. สร้างคำสั่ง SELECT จาก Schema อัตโนมัติ** ตัวโปรแกรมจะอ่านโครงสร้างคอลัมน์จาก Schema ที่ได้ในข้อ 2 จากนั้นครอบชื่อคอลัมน์ด้วย Backtick ผ่านฟังก์ชัน `quote_ident` ทุกครั้ง พร้อมใช้ฟังก์ชัน `CAST(... AS CHAR)` (หรือ `LOWER(HEX(...))` ในกรณีที่เป็นข้อมูลประเภท Binary) เพื่อให้ `sqlx` ดึงข้อมูลทั้งหมดออกมาเป็น String ในรูปแบบมาตรฐานเดียวกันอย่างสม่ำเสมอ

`crates/drugitems-db/src/client.rs:102`

```rust
let exprs: Vec<String> = schema
    .iter()
    .map(|(meta, binary)| {
        let col = quote_ident(&meta.name);
        if *binary {
            format!("LOWER(HEX({col}))")
        } else {
            format!("CAST({col} AS CHAR)")
        }
    })
    .collect();
let stmt = format!("SELECT {} FROM {table_q}", exprs.join(", "));
assert_read_only(&stmt)?;
```

และนี่คือฟังก์ชันเล็ก ๆ อย่าง `quote_ident` ที่ช่วยปิดช่องโหว่ Identifier Injection

```rust
/// Backtick-quote an identifier, escaping any embedded backticks.
fn quote_ident(name: &str) -> String {
    format!("`{}`", name.replace('`', "``"))
}
```

ซึ่งมีการเขียนชุดทดสอบรองรับไว้เช่นกัน

```rust
#[test]
fn quote_ident_escapes_backticks() {
    assert_eq!(quote_ident("drugitems"), "`drugitems`");
    assert_eq!(quote_ident("a`b"), "`a``b`");
}

#[test]
fn generated_select_passes_read_only_guard() {
    let stmt = "SELECT CAST(`icode` AS CHAR), CAST(`name` AS CHAR) FROM `drugitems`";
    assert!(assert_read_only(stmt).is_ok());
}
```

สังเกตได้ว่า แม้ตัวคำสั่ง SQL ในข้อนี้จะถูก Generate ขึ้นมาด้วยระบบของเราเองทั้งหมด แต่โค้ดยังคงนำคำสั่งนั้นส่งเข้า `assert_read_only` ซ้ำอีกรอบ นี่คือการออกแบบเชิงป้องกันที่ตั้งใจซ้อนด่านตรวจ เพราะต้นทุนการประมวลผลของ Guard นั้นต่ำมากเมื่อเทียบกับความปลอดภัยที่ได้รับเพิ่มขึ้น

## 6. ชั้นเสริม จำกัดผลกระทบต่อประสิทธิภาพ

คำว่า Read-only ไม่ได้การันตีว่าตัวฐานข้อมูลจะไม่ได้รับผลกระทบ การสั่ง `SELECT` ข้อมูลทั้งตารางที่ประกอบด้วยคอลัมน์จำนวนมากพร้อมกับการสั่ง `CAST` ซ้ำ ๆ อาจสร้างภาระหนัก (Workload) ให้กับเซิร์ฟเวอร์ของโรงพยาบาลได้ โปรเจกต์นี้จึงมีการควบคุมโหลดการทำงานไว้ 2 ระดับ

2. **ระดับโปรแกรม (Tauri)** มีการคลุม Timeout อีกชั้นหนึ่งสำหรับกระบวนการโดยรวม (`apps/drugitems-app/src/commands.rs:256`)

## 7. ข้อจำกัดจริงที่ต้องยอมรับ (Limitations)

ในการออกแบบระบบ ไม่มีวิธีใดที่สมบูรณ์แบบโดยไร้ข้อเสีย การเข้าใจข้อจำกัดของกลไกแต่ละตัวจะช่วยให้เราประเมินความเสี่ยงได้แม่นยำขึ้น

- **Keyword Guard ไม่ใช่ SQL Parser ที่สมบูรณ์** ตัวตรวจจับนี้ดูเพียงแค่คำแรกของประโยคเท่านั้น คำสั่งบางชนิดที่ขึ้นต้นด้วย `SELECT` แต่อาจมีผลข้างเคียง เช่น `SELECT ... INTO OUTFILE` (เขียนไฟล์ออกไปข้างนอก) หรือ `SELECT ... FOR UPDATE` (การล็อกแถวข้อมูล) จะสามารถหลุดผ่านชั้นที่ 2 ได้ แต่คำสั่งเหล่านี้จะถูกสกัดไว้ได้ด้วย **ชั้นที่ 1 (บัญชี MySQL ไม่มีสิทธิ์ FILE)** และ **ชั้นที่ 3 (SQL ถูกสร้างจากระบบเอง จึงไม่มีการแนบ FOR UPDATE)**
- **ยากต่อการรองรับฟีเจอร์ใหม่ที่ซับซ้อน** หากในอนาคตมีความจำเป็นต้องใช้คำสั่งอย่าง CTE (`WITH ... SELECT`) เพื่ออ่านข้อมูล Guard จะต้องถูกยกเครื่องใหม่เป็น Full Parser เพื่อให้สามารถจำแนกความแตกต่างระหว่าง `WITH ... SELECT` กับ `WITH ... DELETE` ได้
- **ชั้นที่ 1 พึ่งพาผู้ติดตั้งระบบ** หากผู้ดูแลระบบละเลยและไม่ได้ใช้บัญชี Read-only ตามคำแนะนำ โปรแกรมจะเหลือเกราะป้องกันเพียงชั้นที่ 2 และ 3 ซึ่งทำให้เสียด่านที่มั่นคงที่สุดไป
- **Trade-off ด้านประสิทธิภาพ** การดึงข้อมูลออกมาตรวจสอบทั้งตารางในคราวเดียว (จากเคสใช้งานจริง 657 แถว × 202 คอลัมน์) คือการแลกประสิทธิภาพกับความเรียบง่ายของระบบ หากในอนาคตตารางมีขนาดใหญ่ขึ้นมาก อาจจำเป็นต้องปรับเปลี่ยนไปใช้การแบ่งหน้าข้อมูล (Pagination) แทน

## 8. Checklist สำหรับนำไปประยุกต์ใช้

หากคุณกำลังพัฒนาโปรแกรมที่ต้องเชื่อมต่อกับฐานข้อมูลหลักของระบบอื่น ลองนำแนวทางเหล่านี้ไปปรับใช้ได้ครับ

1. **สร้างบัญชีเฉพาะสำหรับโปรแกรม** กำหนดสิทธิ์ให้น้อยที่สุดเท่าที่จำเป็น (Least Privilege) และตัดสิทธิ์คำสั่งเขียน รวมถึงสิทธิ์อันตรายอย่าง `FILE` ออกเสมอ
2. **สร้าง Allow-list Guard เป็น Pure Function** นำไปวางดักไว้ ณ จุดศูนย์กลางที่ทุกคำสั่งต้องวิ่งผ่าน พร้อมเขียน Unit Test ครอบคลุมทั้ง DML, DDL และคำสั่งแฝงอย่าง `WITH`
3. **ปิดช่องรับ Raw SQL จากผู้ใช้** คำสั่งที่ใช้ควรมาจาก Template คงที่ หรือถูกสร้างขึ้นอัตโนมัติจาก Schema ที่ตรวจสอบแล้วเท่านั้น
4. **ทำความสะอาด Identifier เสมอ** ข้อมูลชื่อตารางหรือคอลัมน์ที่ผู้ใช้กรอกต้องครอบด้วย Escape Identifier (เช่น Backtick ใน MySQL) และค่าข้อมูล (Data Values) ต้องส่งผ่าน Parameter Binding (`?`) เท่านั้น
5. **ควบคุม Connection Pool และกำหนด Timeout ชัดเจน** เพื่อไม่ให้โปรแกรมสร้างภาระจนกระทบกับการทำงานหลักของฐานข้อมูล
6. **แยกประเภทของ Error ให้ชัดเจน** ออกแบบให้ Error จาก Guard แปลกแยกจาก Database Query Error ทั่วไป เพื่อให้ระบุได้ทันทีว่าเป็นจุดบกพร่องในโค้ด

## 9. ท้ายที่สุด

แนวคิด Read-only 3 ชั้นของ DrugItems สรุปใจความสำคัญได้ดังนี้

1. **ชั้นที่ 1 สิทธิ์ของ MySQL** เป็นเกราะที่หนาที่สุด แม้โค้ดจะผิดพลาดเพียงใด เซิร์ฟเวอร์ก็จะปฏิเสธคำสั่งเขียนเสมอ
2. **ชั้นที่ 2 Allow-list Guard ในโค้ด** โค้ดสั้น ๆ ที่ยึดหลัก Fail-closed สามารถเขียน Unit Test เพื่อทดสอบได้ทันทีโดยไม่ต้องต่อฐานข้อมูลจริง
3. **ชั้นที่ 3 การสร้าง SQL เองทั้งหมด** ไม่เปิดรับ SQL จากภายนอก ครอบ Backtick ทุก Identifier ใช้ Parameter Binding ทุกจุด และส่งเข้า Guard ซ้ำอีกรอบเพื่อความมั่นใจ

เกราะป้องกันเหล่านี้ไม่ได้ถูกสร้างขึ้นมาเพื่อให้โค้ดดูซับซ้อน แต่มันถูกสร้างขึ้นเพราะในบริบทของระบบโรงพยาบาล คำว่า **"โปรแกรมนี้อ่านอย่างเดียว ไม่แก้ไขข้อมูลแน่นอน"** ถือเป็นพันธสัญญาที่มีผลต่อความปลอดภัยของผู้ป่วยทุกคน และพันธสัญญาที่เชื่อถือได้มากที่สุด คือ **พันธสัญญาที่ถูกการันตีและบังคับใช้ด้วยโค้ด ไม่ใช่การพึ่งพาเพียงแค่วินัยของคนเขียนโปรแกรม**
