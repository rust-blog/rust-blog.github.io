รายงานการเบิกจ่ายยาแต่ละรอบของโรงพยาบาลสระโบสถ์ เคยต้องใช้เวลาทำกันเป็นครึ่งค่อนวันบนไฟล์ Excel ไฟล์เดียว ลำพังแค่คีย์มือก็เหนื่อยแล้ว เลขทะเบียนคุมยังต้องมานั่งไล่นับต่อจากรอบก่อนด้วยสายตาอีก แถมบางเดือนจู่ๆ ก็มี `#REF!` โผล่ขึ้นมาให้ต้องรื้อทำใหม่กันทั้งแผ่น

Swift Bill เกิดมาเพื่อแก้ปัญหานี้โดยเฉพาะ เป้าหมายของมันเรียบง่ายมาก คือแค่กดปุ่มเดียวแล้วได้ไฟล์ PDF ที่พร้อมเซ็นออกมาเลย แต่กว่าจะไปถึงจุดนั้นได้ ด่านแรกที่ยืนขวางอยู่คือ ...

เราจะดึงข้อมูลออกมาจาก INVS ซึ่งเป็น SQL Server รุ่นเก๋าตัวนี้ได้ยังไง?

## อย่าเพิ่งพูดถึง ODBC

คำตอบแรกที่ทุกคนแนะนำตรงกันคือ ODBC ครับ ซึ่งผมเองก็เชื่อแบบนั้นอยู่พักใหญ่ จนกระทั่งได้มาลองคำนวณต้นทุนในการดูแลจริงๆ

ลองนึกภาพว่าเราต้องเดินไปบอกพี่ๆ ฝ่ายเภสัชกรรมว่า "พี่ครับ รบกวนช่วยติดตั้ง ODBC Driver ตัวนี้ก่อนนะ แล้วอย่าลืมตั้งค่า DSN ให้ชื่อ INVS ด้วยล่ะครับ" พอลองคูณจำนวนเครื่องทั้งหมดในโรงพยาบาลเข้าไป ความสุขในการทำงานวันนั้นแทบจะหายวับไปทันที

นอกจากจะชวนปวดหัวเรื่องการติดตั้งแล้ว ODBC ยังเป็นไลบรารีภาษา C ที่ผูกติดกับแต่ละแพลตฟอร์มอย่างเหนียวแน่น นั่นแปลว่าเราต้องยอมทิ้งความเป็น Single Binary ซึ่งเป็นจุดเด่นที่สุดของ Rust ไปแบบน่าเสียดาย

ผมเลยตัดสินใจลองไปนั่งเปิดอ่านดูจริงๆ ว่า เจ้า SQL Server มันคุยกับไคลเอนต์ด้วยวิธีไหนกันแน่

## SQL Server มันไม่ได้คุยด้วย SQL

ความจริงก็คือ มันคุยด้วยภาษาของตัวเองที่ชื่อว่า TDS (Tabular Data Stream) ซึ่งเป็นโปรโตคอลเก่าแก่ที่มีมาตั้งแต่ยุค Sybase ก่อนที่ Microsoft จะรับช่วงต่อมาด้วยซ้ำ ตัวข้อมูลจะถูกหั่นซอยเป็น packet ย่อยๆ แต่ละ packet มี header สั้นๆ แค่ 8 ไบต์ เอาไว้เก็บประเภท สถานะ ความยาว และลำดับการส่ง ทุกอย่างดูเรียบง่ายกว่าที่ผมคิดไว้เยอะมาก

ขั้นตอนการคุยกันของมันก็ไม่ได้มีอะไรซับซ้อน เริ่มจากเปิด TCP ไปที่พอร์ต 1433 ส่ง PRELOGIN ไปทักทายและถามไถ่กันก่อนว่าจะเข้ารหัสไหม มีฟีเจอร์อะไรที่รองรับบ้าง พอตกลงกันได้ก็ทำ TLS handshake ต่อด้วย LOGIN7 เพื่อส่ง username กับ password ไปยืนยันตัวตน หลังจากนั้นข้อมูลที่เหลือทั้งหมดก็คือ token stream ยาวๆ ก้อนหนึ่ง

คำว่า token stream นี่อธิบายภาพรวมได้เห็นภาพที่สุดแล้วครับ ฝั่งเซิร์ฟเวอร์จะค่อยๆ ทยอยโยน token กลับมาทีละชิ้น `COLMETADATA` จะบอกโครงสร้างของคอลัมน์ `ROW` คือข้อมูลหนึ่งแถว `ENVCHANGE` แจ้งเตือนเวลาสถานะของ session เปลี่ยนแปลง ไล่ไปจนถึง `ERROR` และตบท้ายด้วย `DONE` หน้าที่ของไดรเวอร์มีแค่คอยแกะ token พวกนี้ออกมาให้อยู่ในรูปของแถวข้อมูลที่เราเอาไปใช้งานต่อได้

ส่วนเรื่องที่ทำเอาผมต้องหยุดคิดนิดนึงก็คือ คำสั่งแบบมี parameter อย่าง `WHERE RECEIVE_DATE >= @P1` จริงๆ แล้วมันไม่ได้ส่งไปเป็น SQL string แบบต่อข้อความทื่อๆ แต่จะถูกส่งไปแบบ RPC เพื่อเรียกฟังก์ชัน `sp_executesql` โดยแนบ parameter แยกส่งไปต่างหาก วิธีนี้ทำให้ปลอดภัยจาก SQL Injection แบบชัวร์ๆ แถมยังได้อานิสงส์เรื่อง query plan cache มาใช้แบบฟรีๆ ด้วย

และที่ยอดเยี่ยมไปกว่านั้นคือ มีคนเขียนโปรโตคอลนี้ขึ้นมาด้วย Rust เพียวๆ ไว้เรียบร้อยแล้ว ในชื่อ crate ว่า tiberius

## ประโยคใน README ที่ทำให้วางใจ

เวลาจะหยิบเครื่องมืออะไรมาใช้ ผมมักจะเข้าไปอ่าน README ให้จบก่อนเสมอ แล้วผมก็ไปสะดุดตากับประโยคหนึ่งที่ชอบมาก ในหัวข้อ Non-goals เขาเขียนเคลียร์ชัดเจนเลยว่า ตัวมันไม่มีทั้ง Connection Pool และไม่มี ORM ให้ ถ้าอยากได้สิ่งเหล่านี้ ให้ไปดึง `bb8`, `deadpool` หรือ `mobc` มาต่อยอดเอาเอง

ของที่มีจุดยืนชัดเจนแบบนี้หาได้ไม่ง่ายในโลกของ Rust นะครับ crate ส่วนใหญ่มักพยายามทำตัวเป็นทุกอย่างจนตัวโค้ดบวมเกินจำเป็น แต่ tiberius เลือกที่จะทำหน้าที่เป็นแค่ไดรเวอร์ที่จัดการโปรโตคอล TDS ให้ถูกต้องแม่นยำที่สุดแค่อย่างเดียว พออ่านจบปุ๊บ ผมรู้ทันทีเลยว่านี่แหละคือของที่กำลังตามหา

ข้อมูลสำคัญที่ควรรู้ก่อนหยิบมาใช้งานก็มีอยู่ไม่กี่ข้อครับ

- SQL Server 2022, 2019 และ 2017 มีการรันทดสอบบน CI อยู่ตลอด ส่วนเวอร์ชัน 2008 ถึง 2016 ก็น่าจะใช้งานได้ไม่มีปัญหา แต่ถ้าใครต้องไปเจอกับรุ่น 2005 จำเป็นต้องปิด feature `tds73` ก่อน
- ตัว `Client` ออกแบบมารับ socket ที่ implement trait ของ `futures` ได้โดยตรง ดังนั้นจะเอาไปประกบกับ Tokio, async-std หรือ smol ก็ได้ทั้งนั้น
- ค่าเริ่มต้นของมันจะเปิด `native-tls` กับ `winauth` มาให้ ถ้าไม่ได้คิดจะใช้ ก็แค่สั่งปิด default features แล้วเลือกเปิดเฉพาะตัวที่จำเป็น

สำหรับ Swift Bill ผมเลือกใช้ `rustls` เพราะในเอกสารมีโน้ตเตือนไว้ชัดเจนว่า Security Framework ฝั่ง Apple ดันมีปัญหากับ TLS ของ SQL Server ด้วยเหตุผลบางประการ ใครที่นั่งพัฒนาและเทสงานบน macOS อย่างผม พอได้อ่านประโยคนี้ล่วงหน้า บอกเลยว่าช่วยประหยัดเวลาลองผิดลองถูกไปได้หลายชั่วโมงทีเดียว

```toml
[dependencies]
tiberius = { version = "0.13", default-features = false, features = ["rustls", "chrono"] }
tokio = { version = "1", features = ["full"] }
tokio-util = { version = "0.7", features = ["compat"] }
```

## compat กับความงงของผม

จุดนี้แหละครับที่ทำเอาผมยืนงงไปพักใหญ่ โค้ดจริงจากไฟล์ `crates/swift-bill-db/src/connect.rs` หน้าตาเป็นแบบนี้

```rust
pub async fn connect(db_config: &DbConfig) -> Result<TiberiusClient, DbError> {
  let mut config = Config::new();
  config.host(&db_config.host);
  config.port(db_config.port);
  config.database(&db_config.database);
  config.authentication(AuthMethod::sql_server(
    &db_config.username,
    &db_config.password,
  ));
  config.trust_cert();

  let tcp = TcpStream::connect(config.get_addr())
    .await
    .map_err(|e| DbError::Tcp(e.to_string()))?;

  tcp
    .set_nodelay(true)
    .map_err(|e| DbError::Tcp(e.to_string()))?;

  let client = Client::connect(config, tcp.compat_write())
    .await
    .map_err(|e| DbError::Tds(e.to_string()))?;

  Ok(client)
}
```

ต้นเหตุความงงอยู่ที่ฟังก์ชัน `compat_write()` ครับ ปัญหามันเกิดจากทั้ง Tokio และ futures ต่างคนต่างก็มี trait ชื่อ `AsyncRead` กับ `AsyncWrite` เป็นของตัวเอง แต่นิยามข้างในเขียนไว้คนละแบบ ทำให้โยนใส่กันตรงๆ ไม่ได้ ตัว `tokio_util::compat` เลยต้องเข้ามาทำหน้าที่เป็นตัวกลาง ช่วยแปลง `TcpStream` ของ Tokio ให้กลายเป็น stream ในรูปแบบที่ futures คุ้นเคย นั่นเป็นเหตุผลว่าทำไม type ของ client ถึงออกมาหน้าตาแปลกๆ กลายเป็น `Client<Compat<TcpStream>>` แทนที่จะเป็น `Client<TcpStream>` ทื่อๆ

ส่วนโค้ดที่เหลือ อ่านแวบเดียวก็เข้าใจได้ทันที `get_addr()` จะคืนค่า `host:port` กลับมาให้เราเอาไปเปิด socket ต่อ ด้าน `set_nodelay(true)` อันนี้เป็นคำแนะนำจากทีมผู้พัฒนา tiberius เองเลย เพราะฝั่ง client มีการทำ buffer ข้อมูลไว้ล่วงหน้าอยู่แล้ว การปิด Nagle algorithm ไปเลย จะช่วยให้ request ขนาดเล็กๆ ตอบสนองได้รวดเร็วทันใจกว่า

ส่วน `trust_cert()` เป็นบรรทัดที่ผมชั่งใจอยู่นานที่สุด เพราะมันคือการสั่งปิดระบบตรวจสอบใบรับรองความปลอดภัยทั้งหมด เอกสารเตือนไว้ชัดเจนว่าให้ใช้เฉพาะในเน็ตเวิร์กที่มั่นใจจริงๆ เท่านั้น แต่เนื่องจากระบบของโรงพยาบาลใช้ self-signed certificate และวิ่งอยู่บนระบบ LAN วงปิดที่เราคุมเองได้ทั้งหมด ผมเลยยอมรับความเสี่ยงตรงนี้ได้ แต่ถ้าใครมีสิทธิ์เข้าไปจัดการฝั่งเซิร์ฟเวอร์ได้เอง แนะนำให้ไปใช้ `trust_cert_ca()` จะปลอดภัยและรัดกุมกว่ามาก

อีกจุดหนึ่งที่ผมเพิ่งมารู้ตอนทำก็คือ SQL Server จะบังคับทำ TLS handshake ในขั้นตอนล็อกอินเสมอ ต่อให้เราตั้งค่าว่าไม่ต้องการเข้ารหัสข้อมูลก็ตาม ปัญหาเรื่องใบรับรองมันเลยโผล่มากวนใจตั้งแต่จังหวะเริ่มต่อสายเลย ไม่ได้รอให้เราไปเจอตอนดึงข้อมูล

ด้านการจัดการ error ผมแบ่งออกเป็นสองระดับโดยใช้ `thiserror` เพื่อให้รู้ได้ทันทีว่าระบบพังตั้งแต่ชั้น TCP หรือไปติดขัดที่ระดับโปรโตคอล TDS

```rust
#[derive(Debug, thiserror::Error)]
pub enum DbError {
  #[error("TCP connection failed: {0}")]
  Tcp(String),
  #[error("TDS connection failed: {0}")]
  Tds(String),
}
```

## วันที่ TOTAL_COST กลายเป็น DECIMAL

เคสนี้เป็นเรื่องที่กินเวลาผมไปเกือบครึ่งวัน และเป็นที่มาว่าทำไมโค้ดอ่านตัวเลขถึงต้องมีฟังก์ชัน helper แยกออกมาโดยเฉพาะ

tiberius จัดการเรื่อง data type ค่อนข้างเข้มงวดมาก ถ้าเราขออ่านค่าแบบ `f64` แต่ชนิดข้อมูลจริงในตารางเป็น `DECIMAL` มันจะโยน error ใส่หน้าทันทีโดยไม่มีการแปลงค่าให้อัตโนมัติ แต่ปัญหาคือระบบรุ่นเก่าๆ มักจะกำหนดชนิดข้อมูลของคอลัมน์เดียวกันไว้ไม่เหมือนกันในแต่ละตาราง บางที่ใช้ `FLOAT(53)` บางตารางเป็น `REAL` พอไปอีกตารางกลับเป็น `DECIMAL` ซะงั้น โค้ดชุดเดิมที่เคยคิดว่าข้อมูลคงมีแบบเดียว ก็เลยพังทันทีเมื่อต้องมาเจอกับข้อมูลจริงๆ หน้างาน

ทางออกของผมคือการเขียนให้มันลองเดาและแปลงทีละ type ไปเลย

```rust
fn get_f64(row: &Row, col: &str) -> Option<f64> {
  if let Ok(Some(v)) = row.try_get::<f64, _>(col) {
    return Some(v);
  }
  if let Ok(Some(v)) = row.try_get::<f32, _>(col) {
    return Some(f64::from(v));
  }
  if let Ok(Some(v)) = row.try_get::<tiberius::numeric::Numeric, _>(col) {
    let s = format!("{v}");
    if let Ok(f) = s.parse::<f64>() {
      return Some(f);
    }
  }
  None
}
```

`Numeric` คือ type พิเศษของ tiberius ที่เอาไว้รับมือกับ `DECIMAL` และ `NUMERIC` ซึ่งมันไม่มีฟังก์ชันสำเร็จรูปสำหรับแปลงเป็น float ตรงๆ แต่มี trait `Display` ติดมาให้ ผมเลยใช้วิธีแปลงมันออกมาเป็น string ก่อน แล้วค่อยเอา string นั้นมา parse เป็น `f64` อีกทีหนึ่ง

เรื่องฟอร์แมตวันที่ก็ชวนปวดหัวไม่แพ้กันเลยครับ ระบบเดิมบางจุดเก็บวันที่เป็นข้อความแบบ `YYYYMMDD` แต่บางตารางกลับคั่นด้วยขีดเป็น `YYYY-MM-DD` ฟังก์ชันที่เราเขียนขึ้นมาเลยต้องใช้วิธีเช็กความยาวของข้อความเพื่อเดารูปแบบเอา ส่วนแถวไหนที่อ่านวันที่ไม่สำเร็จจริงๆ เราก็เลือกที่จะปล่อยข้ามไปเงียบๆ เพราะยังไงก็เอาไปออกรายงานไม่ได้อยู่ดี

```rust
fn parse_receive_date(raw: &str) -> Option<NaiveDate> {
  let trimmed = raw.trim();
  if trimmed.len() == 8 {
    NaiveDate::parse_from_str(trimmed, "%Y%m%d").ok()
  } else if trimmed.len() == 10 {
    NaiveDate::parse_from_str(trimmed, "%Y-%m-%d").ok()
  } else {
    None
  }
}
```

เอาจริงๆ โค้ดส่วนนี้ผมแอบรู้สึกผิดนิดๆ ตอนเขียน เพราะการปล่อยให้ข้อมูลหลุดหายไปเงียบๆ ไม่ใช่แนวปฏิบัติที่ดีสำหรับงานด้านบัญชีและการเงินเลย แต่ในชีวิตจริง รายงานพวกนี้จะต้องผ่านสายตาคนตรวจทานซ้ำอีกรอบเสมอ และข้อมูลแถวที่วันที่พังจริงๆ ก็มีสัดส่วนน้อยมากๆ เราเลยตัดสินใจเลือกทางที่ง่ายและคล่องตัวไว้ก่อน เรื่องแบบนี้ไม่มีสูตรสำเร็จตายตัวครับ อยู่ที่ว่าเรารับความเสี่ยงได้ในระดับไหน

## ไม่มี pool ก็ไม่ตาย

tiberius ไม่ได้แถมระบบ connection pool มาให้ และผมก็ไม่ได้หามาใส่เพิ่มด้วย ทุกคำสั่งที่ Swift Bill รัน จะใช้วิธีเปิด connection ใหม่ขึ้นมา พอทำงานเสร็จก็ปิดทิ้งทันที

เหตุผลเบื้องหลังมันบ้านๆ มากครับ เพราะโปรแกรมนี้ถูกเปิดใช้งานแค่เดือนละไม่กี่ครั้ง การทำ TCP และ TLS handshake บนเครือข่าย LAN เดียวกันกินเวลาแค่ไม่กี่มิลลิวินาทีเท่านั้น การไปเปิด connection ค้างเติ่งไว้ให้มัน idle เล่นๆ แทบไม่ได้ช่วยอะไรเลย มีแต่จะไปเพิ่มภาระให้เซิร์ฟเวอร์ต้องคอยแบกรับ connection ค้างไว้เปล่าๆ

ถ้าถึงวันที่โปรแกรมมีคนใช้งานพร้อมๆ กันเยอะขึ้น หรือลองวัดประสิทธิภาพแล้วพบว่าขั้นตอนเชื่อมต่อมันช้าจนกลายเป็นคอขวดจริงๆ เมื่อนั้นค่อยเอา `bb8` หรือ `deadpool` มาเสียบเพิ่มทีหลังก็ยังทัน ตัวอย่างการต่อใช้งานก็มีสอนไว้ละเอียดยิบใน repo ของ tiberius เอง แทบไม่ต้องรื้อแก้โค้ดเดิมเลยสักนิด

สิ่งที่ผมมองว่าสำคัญกว่ามากๆ คือเรื่องสิทธิ์การเข้าถึงของ database user ครับ โปรเจกต์นี้ทั้งระบบไม่มีคำสั่งเขียนข้อมูลลงไปแม้แต่บรรทัดเดียว ดังนั้นแค่ให้ DBA สร้างบัญชีที่มีสิทธิ์แค่ `SELECT` อย่างเดียวก็พอแล้ว นี่คือปราการด่านสุดท้ายบนฝั่งเซิร์ฟเวอร์ ที่จะการันตีว่าต่อให้โค้ดฝั่งเราจะบั๊กหรือพังแค่ไหน มันก็ไม่มีทางหลุดไปกระทบกับข้อมูลจริงบนฐานข้อมูลได้อย่างแน่นอน

ส่วนรหัสผ่านสำหรับเข้า INVS เราก็ไม่ได้เซฟเก็บเป็น plaintext โต้งๆ นะครับ ฝั่งแอปพลิเคชันจะนำไปเข้ารหัสผ่าน `encryptman` (AES-256-GCM) ก่อน แล้วฝากตัว master key ไว้ใน OS Keychain ผ่าน `encryptman-keyring` ต่อให้มีใครก๊อปปี้ไฟล์ config ไปเปิดบนเครื่องอื่น ก็ไม่มีทางแกะรหัสผ่านออกมาอ่านได้อยู่ดี ซึ่งดีเทลเรื่องนี้ค่อนข้างยาว ไว้วันหลังค่อยแยกมาเล่าให้ฟังเป็นอีกบทความหนึ่งครับ

## ทิ้งท้าย

TDS อาจจะเป็นโปรโตคอลเก่าแก่ที่มีอายุเกือบสามสิบปี แต่การได้ลองนั่งแกะอ่านสเปกของมันสักครั้ง กลับเปลี่ยนมุมมองที่ผมมีต่อ SQL Server ไปอย่างสิ้นเชิง จากเดิมที่เคยมองว่าเป็นกล่องดำปริศนาที่ต้องคอยพึ่งพาไดรเวอร์คนอื่น กลายมาเป็นเซิร์ฟเวอร์ธรรมดาๆ ตัวหนึ่งที่พร้อมจะพูดคุยกับเราตรงๆ ผ่านภาษาที่ถึงจะดูโบราณไปหน่อย แต่ก็ตรงไปตรงมาและชัดเจนในตัวเอง

tiberius ช่วยย่อยภาษาเหล่านั้นออกมาให้กลายเป็นโค้ดภาษา Rust เพียงแค่สิบกว่าบรรทัดที่อ่านแล้วเข้าใจได้แบบกระจ่างแจ้ง ไม่ต้องพึ่งพาเวทมนตร์แปลกๆ ชวนปวดหัว ไม่มี FFI ชวนหวาดเสียว และที่ฟินที่สุดคือ ไม่ต้องคอยบอกให้ผู้ใช้งานไปไล่ติดตั้งโปรแกรมอะไรเพิ่มก่อนเปิดใช้งานโปรแกรมเลย

ถ้าใครกำลังเจอปัญหาหรือโจทย์แนวๆ นี้อยู่ ลองสละเวลาเข้าไปเปิดสเปกดูภาษาที่ระบบพวกนี้มันคุยกันดูครับ บางทีคำตอบของปัญหาอาจจะไม่ได้อยู่ที่การวิ่งตามไลบรารีใหม่ล่าสุด แต่อาจจะอยู่ที่การยอมถอยลงมาดูว่า เครื่องจักรยุคเก่าพวกนี้มันสื่อสารกันยังไงมาตั้งแต่แรกเริ่มนั่นเอง
