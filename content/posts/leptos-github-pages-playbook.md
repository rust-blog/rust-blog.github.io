บทความนี้ผมตั้งใจเขียนขึ้นมาเป็น **Playbook** โดยมีเป้าหมายมีเพียงอย่างเดียวคือ เมื่อเรากลับมาอ่านอีกครั้ง (หรือในวันที่ CI พังขึ้นมากลางคัน) เราจะเข้าใจได้ทันทีว่า `deploy.yml` แต่ละบล็อกทำหน้าที่อะไร **ทำไม** ถึงต้องเขียนแบบนั้น และถ้ามีอะไรพัง สาเหตุเกิดมาจากจุดไหน

โปรเจกต์ต้นแบบที่ใช้อ้างอิงก็คือบล็อก [rust-blog](https://github.com/rust-blog/rust-blog.github.io) แห่งนี้นี่เอง - ตัวเว็บเป็นสถาปัตยกรรม Leptos 0.8 แบบ CSR (Client-Side Rendering) + Trunk + Wasm ที่จัดการ deploy ทั้งหมดผ่านไฟล์ `.github/workflows/deploy.yml` เพียงไฟล์เดียว โครงสร้างนี้สามารถนำไปปรับใช้กับโปรเจกต์ Leptos CSR ทุกตัวที่ build ด้วย Trunk ได้ทันที แต่**ไม่สามารถใช้กับ Leptos SSR ได้** เนื่องจาก GitHub Pages เป็น Static Hosting ล้วน ไม่มี server runtime ไว้สำหรับรัน server function

## 1. Mental model: เกิดอะไรขึ้นเมื่อ push โค้ดหนึ่งครั้ง

เมื่อ push เข้า `main` แล้ว workflow จะทำงานเป็นสองช่วงต่อกันคือ **Build Job** (เตรียมสิ่งที่ต้องการเผยแพร่) และ **Deploy Job** (เผยแพร่) โดยมี Artifact ของโฟลเดอร์ `dist/` เป็นตัวส่งต่อระหว่างกัน

### 1.1 Build Job - `runs-on: ubuntu-latest`

1. **Checkout** - ดึงโค้ดลงเครื่อง พร้อมตั้ง `persist-credentials: false` เพื่อไม่ให้ Credential ค้างอยู่ในเครื่อง หากขั้นนี้พัง Build จะหยุดทันที
2. **ติดตั้ง Rust Toolchain** - ใช้ Channel, Target (`wasm32-unknown-unknown`) และ Component ตาม `rust-toolchain.toml` เพื่อให้ CI กับเครื่อง Dev ใช้เวอร์ชันเดียวกัน ถ้าไม่มี Target นี้ จะคอมไพล์ Wasm ไม่ได้
3. **Cache Cargo** - ดึง Cache ของ Dependency กลับมาใช้ ลดเวลาที่ต้องคอมไพล์ซ้ำหลายนาที ขั้นนี้พังได้แค่ทำให้ Build ช้าลง ไม่ทำให้ Build ล้ม
4. **ด่านคุณภาพ** - `fmt` → `clippy` (ยิง Target wasm32) → `test` ถ้าไม่ผ่านข้อใดข้อหนึ่ง จะไม่มีการ Deploy
5. **ด่าน Supply Chain** - `cargo-audit` → `cargo-deny` ถ้าไม่ผ่าน จะไม่มีการ Deploy เช่นกัน
6. **Trunk Build** - รัน `trunk build --release --public-url /` เพื่อประกอบทุกอย่างออกมาเป็นโฟลเดอร์ `dist/`
7. **post_build** - สร้างหน้า Static รายโพสต์สำหรับ SEO/OG ถ้าขาดขั้นนี้ ลิงก์ที่แชร์จะไม่มีการ์ดข้อมูล และหน้าโพสต์จะเหลือแค่ 404 Fallback
8. **SPA Fallback** - คัดลอก `index.html` เป็น `404.html` ไม่งั้นกด Refresh ที่ Deep Link แล้วจะเจอ 404
9. **Upload Artifact** - ส่งโฟลเดอร์ `dist/` ขึ้นเป็น Artifact เพื่อส่งต่อให้ Deploy Job

### 1.2 Deploy Job - `needs: build`

Deploy Job จะเริ่มทำงานก็ต่อเมื่อ Build Job สำเร็จเท่านั้น (`needs: build`) ตัว Job นี้ถือสิทธิ์ `pages: write` และ `id-token: write` เป็นการเฉพาะ ไม่ Checkout และไม่รันโค้ดของโปรเจกต์เลย - เรียก `deploy-pages` เพื่อนำ Artifact ไปเผยแพร่ที่ Environment ชื่อ `github-pages` เท่านั้น จากนั้นเว็บจริงจะขึ้นที่ `https://rust-blog.github.io`

หลักการสำคัญ 3 ข้อที่ workflow นี้ยึดถือ:

1. **แยก Build ออกจาก Deploy ชัดเจน** - โค้ดที่เราอาจควบคุมไม่ได้ทั้งหมด (เช่น dependency ภายนอก หรือ build script) จะถูกกักบริเวณให้อยู่ใน Job ที่มีสิทธิ์แค่อ่าน (Read-only) ส่วน Job ที่มีสิทธิ์เขียน (Deploy) มีหน้าที่เพียงแค่นำ Artifact ที่ผ่านการ build แล้วไปเผยแพร่เท่านั้น
2. **ใช้ Artifact เป็นสะพานเชื่อม** - ไม่ต้องสร้าง branch `gh-pages` มาปะปนกับ source code ใน repo และไม่มี state ใด ๆ ตกค้างข้ามระหว่าง Job
3. **ไม่พึ่งพา Secret แม้แต่ตัวเดียว** - ระบบยืนยันตัวตนทั้งหมดทำงานผ่าน OIDC (`id-token`) เพื่อขอ Token ชั่วคราวที่มีอายุสั้นมาก จึงไม่มี Personal Access Token (PAT) ให้ต้องคอย rotate หรือกังวลว่าจะรั่วไหล

## 2. ก่อนเริ่ม: Checklist การตั้งค่าครั้งเดียวที่ต้องตรวจ

การตั้งค่าที่ต้องทำก่อน Push ครั้งแรกมีทั้งหมด 5 ข้อ แต่ละข้อมาพร้อมตำแหน่งที่ตั้งค่าและผลกระทบหากลืม

1. **ตั้ง Pages Source เป็น GitHub Actions** - ตั้งค่าที่ Settings → Pages → Build and deployment ถ้าไม่ตั้ง Workflow จะอัปโหลด Artifact สำเร็จแต่ขั้นตอน Deploy ไม่ทำงาน (หรือระบบยังวิ่งไปหาแบบ Deploy from a branch แทน)
2. **ระบุค่า `--public-url` ให้ตรงกับประเภทของ Repo** - แก้ใน `deploy.yml` ถ้าไม่ตรง เบราว์เซอร์จะหา Asset ไม่เจอ (404) ส่งผลให้หน้าเว็บขาวโพลน
3. **ใส่ Target `wasm32-unknown-unknown` ใน `rust-toolchain.toml`** - ถ้าไม่มี CI จะพังตั้งแต่ขั้นตอนการรัน Clippy
4. **Commit ไฟล์ `Cargo.lock` ขึ้น Git เสมอ** - ถ้าไม่ Commit ผลการ Build จะไม่แน่นอน (Non-reproducible) เนื่องจากเวอร์ชัน Dependency อาจขยับไปเอง
5. **เพิ่ม `dist/` ลงใน `.gitignore`** - ถ้าไม่เพิ่ม อาจเผลอ Commit ไฟล์ผลลัพธ์จากการ Build ปะปนเข้า Git History ทุกครั้ง

### การเลือกค่า `--public-url` ให้ถูกต้อง (จุดที่ผิดพลาดบ่อยที่สุด)

- **User/Org Site** (ชื่อ Repo เป็น `<user>.github.io`) - ตัวเว็บอยู่ที่ `https://<user>.github.io/` จึงต้องใช้ `--public-url /`
- **Project Site** (ชื่อ Repo ทั่วไป) - ตัวเว็บอยู่ที่ `https://<user>.github.io/<repo>/` จึงต้องใช้ `--public-url /<repo>/`

Trunk จะนำค่านี้ไปเขียนเป็น Base Path สำหรับอ้างอิงไฟล์ `.wasm`, JS Glue code และ CSS ลงใน `index.html` 

หากโปรเจกต์ของคุณเป็นแบบ Project Site ที่โฮสต์อยู่ใต้ `/<repo>/` แต่ดันใส่เป็น `--public-url /` เบราว์เซอร์จะพยายามวิ่งไปดาวน์โหลดไฟล์จาก Root Domain (`https://<user>.github.io/...`) ซึ่งไม่มีไฟล์เหล่านั้นอยู่จริง ผลลัพธ์คือ **หน้าเว็บจะขาวโพลน (Blank page)** โดยไม่มีข้อความ Error เตือนให้เห็นชัดเจนบนหน้าจอ (ต้องเปิดดูใน Browser Console ถึงจะเจอ 404)

## 3. เจาะลึก deploy.yml ทีละส่วน

### 3.1 `name` / `on` - Trigger และเงื่อนไขการทำงาน

```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:
```

**ทำหน้าที่อะไร** - สั่งให้ Workflow เริ่มทำงานทุกครั้งที่มีการ Push โค้ดเข้าสู่ Branch `main` และเปิดปุ่มให้เราสามารถกดสั่งรันด้วยตัวเอง (Manual trigger) ผ่านแท็บ Actions ได้ทุกเมื่อ

**ทำไมต้องเขียนแบบนี้** - เรายึดแนวคิดแบบ Trunk-Based Development โดยมองว่า "Branch main คือสายการผลิตหลักเพียงหนึ่งเดียว" ส่วนการเปิดใช้ `workflow_dispatch` ไว้นั้นมีประโยชน์มากเวลาที่เราต้องการสั่ง Deploy ใหม่หลังจากไปปรับแต่งการตั้งค่าภายนอก (เช่น ไปเปลี่ยนการตั้งค่า Pages ในหน้า Settings) โดยไม่จำเป็นต้องสร้าง Commit เปล่า (Dummy commit) ขึ้นมาเพื่อหลอกให้ Workflow ทำงาน

**ความเสี่ยงและข้อควรระวัง**

- **ไม่มี Trigger สำหรับ Pull Request (PR) ในไฟล์นี้**: แปลว่า Quality Gates ทุกด่าน (fmt / clippy / test / audit) จะทำงานก็ต่อเมื่อโค้ดถูก Merge เข้า `main` แล้วเท่านั้น หากมีอะไรพัง เราจะรู้ตัวก็ต่อเมื่อโค้ดขึ้นสายการผลิตหลักไปแล้ว หากทำงานร่วมกันเป็นทีม แนะนำให้แยก Workflow อีกชุดไว้สำหรับตรวจ PR โดยเฉพาะ หรือเปิดใช้งาน Branch Protection Rules ร่วมกับ Required Status Checks
- **Push เข้า main แปลว่า Deploy ขึ้น Production ทันที**: เนื่องจากไม่มีขั้นตอน Staging คั่นกลาง จึงควรเปิด Branch Protection เพื่อป้องกันไม่ให้สมาชิกเผลอ Push โค้ดตรงเข้า `main` โดยไม่ผ่านการรีวิว
- **แค่แก้ README ระบบก็สั่ง Deploy ใหม่ (เปลืองเวลา CI)**: หากต้องการประหยัดโควตาเวลา สามารถกำหนด `paths:` หรือ `paths-ignore:` เพิ่มเติมได้ แต่ก็ต้องระวังอย่ากำหนดแคบจนเกินไป เพราะอาจทำให้ระบบไม่ยอม Deploy ในวันที่เราจำเป็นต้องแก้ไฟล์รอบนอก

### 3.2 `permissions` - ยึดหลัก Least Privilege (จำกัดสิทธิ์ให้น้อยที่สุด)

```yaml
permissions:
  contents: read
```

**ทำหน้าที่อะไร** - ล็อกสิทธิ์ของ `GITHUB_TOKEN` ในระดับ Workflow เริ่มต้นให้อ่านโค้ดได้เพียงอย่างเดียว (Read-only) แล้วปล่อยให้ Job ที่มีความจำเป็นจริง ๆ ทำการขอยกระดับสิทธิ์เฉพาะตัวขึ้นมาเอง

**ทำไมต้องเขียนแบบนี้** - เพื่อรับมือกับความเสี่ยงเรื่อง Supply Chain Attacks หากเกิดกรณีที่ Dependency หรือ Build Script ภายนอกถูกแทรกแซง สิ่งเลวร้ายที่สุดที่สคริปต์เหล่านั้นจะทำได้คือการอ่านโค้ดและใช้ทรัพยากรบน Runner เท่านั้น ไม่สามารถนำ Token ไป Push โค้ดหรือดัดแปลงข้อมูลใน Repository ได้เลย แม้ว่า Token ของ Actions จะมีอายุจำกัดเพียงแค่จบการรันรอบนั้น ๆ แต่การจำกัด Scope ให้แคบไว้ก่อนถือเป็นแนวป้องกัน (Defense in Depth) ที่คุ้มค่าและไม่มีต้นทุนอะไรเพิ่มเติม

**ความเสี่ยงและข้อสังเกต** - หากในอนาคตเรามีการเพิ่ม Step ใหม่ที่จำเป็นต้องใช้สิทธิ์เพิ่มเติมแต่ลืมปรับแก้ `permissions` ตัว Job นั้นจะทำงานล้มเหลวทันที ซึ่งถือเป็น **ความล้มเหลวที่ปลอดภัย (Fail-safe)** เพราะทำให้เรารู้ตัวทันที ดีกว่าการเปิดสิทธิ์แบบกว้างเผื่อไว้ตั้งแต่แรก

ข้อดีของการวางโครงสร้างนี้คือ ฝั่ง Deploy Job จะประกาศขอสิทธิ์ `pages: write` และ `id-token: write` เฉพาะในขอบเขตของตัวเองเท่านั้น ทำให้ไม่มี Secret ระดับ Repository ให้ต้องมาคอยกังวลเลย

### 3.3 `concurrency` - จัดการคิวและป้องกันการ Deploy ซ้อนกัน

```yaml
concurrency:
  group: pages
  cancel-in-progress: true
```

**ทำหน้าที่อะไร** - กำหนดให้ Workflow ภายใต้กลุ่ม `pages` ทำงานได้ทีละ 1 รายการเท่านั้น และเมื่อมี Run ใหม่ถูกส่งเข้ามา ระบบจะยกเลิก Run ก่อนหน้าที่ยังค้างอยู่ทันที

**ทำไมต้องเขียนแบบนี้** - เพื่อป้องกันปัญหา Race Condition เช่น กรณีที่ Run เก่า Build ช้ากว่า Run ใหม่ แล้วกลายเป็นว่า Artifact รุ่นเก่าดันถูก Deploy ไปทับรุ่นใหม่ทีหลัง นอกจากนี้ยังช่วยประหยัดเวลาการใช้งาน Runner (CI Minutes) อีกด้วย

**ความเสี่ยงสำคัญที่ต้องเข้าใจ (Deep Dive)**

สังเกตว่า Starter Workflow ทางการของ GitHub สำหรับ Pages มักจะตั้งค่าเป็น `cancel-in-progress: false` พร้อมระบุเหตุผลว่า *"อย่ายกเลิก Run ที่กำลังดำเนินการอยู่กลางคัน เพื่อให้มั่นใจว่า Production Deployment จะทำงานจนจบสมบูรณ์"*

สาเหตุเบื้องหลังคือ GitHub Pages อนุญาตให้มีสถานะ Deployment ที่ค้างอยู่ได้เพียง 1 รายการต่อหนึ่ง Git Reference หาก Run A กำลังยิง Deploy ขึ้น Pages อยู่ แล้วถูก Run B สั่งยกเลิกระหว่างทาง ตัว Deployment ของ Run A อาจค้างสถานะ "in-progress" ส่งผลให้ Run B ไม่สามารถเริ่มกระบวนการ Deploy ของตัวเองได้ (ดูปัญหาเพิ่มเติมได้ที่ [actions/deploy-pages#118](https://github.com/actions/deploy-pages/issues/118)) และหากไม่มี Run C ตามมา ผลลัพธ์คือโค้ดของ Run B ก็จะไม่ได้ขึ้น Production เลย

สำหรับใน Repository นี้ เราเลือกใช้ `true` เพราะต้องการให้เว็บไซต์แสดงผลโค้ดเวอร์ชันล่าสุดเสมอ ซึ่งก็ต้องยอมรับความเสี่ยงข้างต้นเล็กน้อย **ข้อควรจำเวลาเกิดปัญหา:** หากพบว่าขั้นตอน Deploy ล้มเหลวด้วยข้อความทำนอง *"cannot start a new deployment while one is in progress"* ให้ปรับค่าเป็น `false` (หรือกด Re-run ใหม่อีกครั้ง) ทั้งนี้ สำหรับระบบระดับ Production ทั่วไป การเลือกใช้ `false` แล้วปล่อยให้งานเข้าคิวรอจนเสร็จตามลำดับจะเป็นตัวเลือกที่ปลอดภัยกว่า

**เกร็ดเพิ่มเติม:** การตั้งค่า `concurrency` ไว้ที่ระดับบนสุดของ Workflow จะครอบคลุมทั้งขั้นตอน Build และ Deploy นั่นแปลว่า Run ใหม่อาจยกเลิกขั้นตอน Build เก่าได้ด้วย ซึ่งช่วยประหยัดเวลาได้ดี แต่หากต้องการยกเลิกเฉพาะขั้นตอน Build โดยไม่ให้กระทบขั้นตอน Deploy เลย แนะนำให้ย้ายบล็อก `concurrency` ลงไประบุเฉพาะภายในระดับ Job แทน

### 3.4 `runs-on: ubuntu-latest` - สภาพแวดล้อมของ Runner

**ทำไมต้องเป็นตัวนี้** - เป็นตัวเลือกที่ประหยัดโควตาเวลาและเริ่มต้นทำงานได้เร็วที่สุดในบรรดา GitHub-hosted runners ทั้งหมด

**ความเสี่ยงที่ต้องระวัง** - คำว่า `latest` ถือเป็น Moving target หรือเป้าหมายที่เลื่อนได้ตลอดเวลา ในวันที่ GitHub มีการอัปเดต Environment Image ใหม่ (เช่น มีการปรับเวอร์ชันของ System Libraries หรือ Linker) การ Build ของเราอาจพังได้กะทันหันโดยที่ยังไม่มีใครแตะต้องโค้ดเลยแม้แต่บรรทัดเดียว หากต้องการความเสถียรสูงสุด (Deterministic) แนะนำให้ระบุเวอร์ชันเจาะจงเป็น `ubuntu-24.04`

### 3.5 Checkout - Pin ด้วย Commit SHA และไม่บันทึก Credential ค้างไว้

```yaml
- name: Checkout
  uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
  with:
    persist-credentials: false
```

**ทำหน้าที่อะไร** - ดึง Source Code ใน Repository มาลงบนเครื่อง Runner (โดยค่าเริ่มต้นจะไม่ดึง Git History มาทั้งหมดเพื่อประหยัดเวลา)

**ทำไมต้อง Pin ด้วย SHA แทนการใช้ Tag** - การใช้ Tag เช่น `@v7` หรือ `@main` เป็น Pointer ที่เจ้าของ Action สามารถ *ย้ายไปชี้ที่ Commit ไหนก็ได้* หากบัญชีผู้ดูแล Action ถูกแฮก ผู้โจมตีก็สามารถแก้ Tag ให้หันไปชี้ที่โค้ดอันตรายได้ทันที (ซึ่งเป็นรูปแบบการโจมตี Supply Chain ที่เคยเกิดขึ้นจริงในชุมชน CI/CD) ในขณะที่ Commit SHA เป็นค่าแฮชที่ไม่สามารถเปลี่ยนแปลงเนื้อหาได้ จึงเป็นจุดอ้างอิงที่มั่นคงและเชื่อถือได้สูงสุด ส่วนคอมเมนต์ `# v7.0.1` ด้านหลัง เราใส่ไว้เพื่อให้เพื่อนร่วมทีมยังคงอ่านออกว่าเทียบเท่ากับเวอร์ชันใด

**ทำไมต้องตั้ง `persist-credentials: false`** - พฤติกรรมดั้งเดิมของ `actions/checkout` จะนำ Token ไปฝังไว้ใน Git Config ของเครื่อง Runner อัตโนมัติ เพื่ออำนวยความสะดวกให้คำสั่ง Git ใน Step ถัด ๆ ไปสามารถ Push โค้ดกลับได้ แต่เนื่องจาก Build Job ของเราไม่มีความจำเป็นต้องแก้ไขหรือ Push โค้ดใด ๆ การปิดคุณสมบัตินี้จึงเป็นการตัดวงจร ไม่เปิดโอกาสให้มัลแวร์หรือสคริปต์แปลกปลอมในขั้นตอน Build แอบขโมย Token ออกไปได้ (Defense in Depth)

**ข้อแลกเปลี่ยนและสิ่งที่ต้องดูแล** - ข้อเสียของการใช้ Commit SHA คือมนุษย์อ่านไม่ออกว่าคือเวอร์ชันใด และไม่ได้รับการอัปเดตแบบอัตโนมัติ จึงจำเป็นต้องมี Bot เช่น Renovate (ใน Repo นี้มีการตั้งค่า `renovate.json` เอาไว้แล้ว) หรือ Dependabot คอยเปิด PR ช่วยอัปเดต SHA ให้อย่างสม่ำเสมอ มิฉะนั้นโค้ดของเราอาจตกค้างอยู่ที่ SHA เก่าตลอดไปโดยไม่รู้ตัว

### 3.6 Rust Toolchain - กำหนด Single Source of Truth ด้วยไฟล์แยก

```yaml
- name: Install Rust toolchain
  uses: dtolnay/rust-toolchain@f8be11a05b1d4f3fcebe6410cc16743212b999b0 # 1.98.0
  # Channel, targets, and components are pinned via rust-toolchain.toml
```

```toml
# rust-toolchain.toml
[toolchain]
channel = "1.98.0"
targets = ["wasm32-unknown-unknown"]
components = ["rustfmt", "clippy"]
```

**ทำไมต้องเขียนแบบนี้** - หากเรากำหนด `channel: stable` ไว้ในไฟล์ YAML โดยตรง เมื่อใดก็ตามที่ Rust ปล่อยอัปเดตเวอร์ชัน Stable ใหม่ ตัว CI ก็จะเปลี่ยนเวอร์ชันตามไปเองแบบเงียบ ๆ แต่การล็อกเวอร์ชันผ่านไฟล์ `rust-toolchain.toml` จะทำให้ **ทั้งเครื่อง Developer ในทีม และเครื่อง CI ใช้ Rust Toolchain เวอร์ชันเดียวกันอย่างแน่นอน** ปัญหาประเภท "ในเครื่องผมรันผ่าน แต่ทำไมบน CI พัง" จะหมดไป และยังช่วยให้ผลลัพธ์ของ Clippy หรือ Rustfmt คาดเดาได้ ไม่เปลี่ยนไปตามเวอร์ชันคอมไพเลอร์

**ความเสี่ยงและข้อควรระวัง** - หากลืมระบุ Target `wasm32-unknown-unknown` ลงในไฟล์นี้ CI จะพังทันทีตั้งแต่ขั้นตอนการรัน Clippy (ซึ่งยังถือว่าดีตรงที่ Fail เร็วและแจ้งสาเหตุตรงไปตรงมา) นอกจากนี้ การอัปเกรด Rust จะไม่ได้เปลี่ยนไปตามคำสั่ง `rustup update` ของแต่ละคนอีกต่อไป แต่จะกลายเป็น "งานที่ทีมต้องตั้งใจทำและทดสอบร่วมกัน" ซึ่งถือเป็นข้อดีด้านความเสถียรที่แลกมาด้วยขั้นตอนการดูแล

### 3.7 Cache - ย่นเวลา Build ภายใต้ความเสี่ยงที่ควบคุมได้

```yaml
- name: Cache cargo
  uses: Swatinem/rust-cache@6323deb102c322ba6fcbdcafc7e3dddab59af2b6 # v2.9.2
```

**ทำไมต้องใช้** - โปรเจกต์ Leptos + Wasm มีการคอมไพล์ Dependency ค่อนข้างเยอะ การเปิดใช้งาน Cache สำหรับไดเรกทอรี `~/.cargo` และโฟลเดอร์ `target/` จะช่วยลดเวลาการคอมไพล์โค้ดซ้ำเดิมไปได้หลายนาทีต่อหนึ่งรอบการรัน

**ความเสี่ยงและการรับมือ** - ปัญหา Cache ตกค้างหรือเสียหาย (Cache Corruption) อาจทำให้เกิดอาการชวนปวดหัว เช่น "โค้ดเดิมรันใน Local ผ่านฉลุย แต่บน CI กลับรันไม่ผ่าน" ซึ่งวิธีแก้ไขคือการเข้าไปกดลบ Cache ในหน้า Actions Management หรือสั่ง Bump Key ใหม่ 

ส่วนประเด็นเรื่องความปลอดภัย เช่น Cache Poisoning จาก Pull Request แปลกปลอมนั้น ตัว Action `Swatinem/rust-cache` มีการจัดการแยก Cache Key ตาม Branch และ Ref ไว้ให้แล้ว แต่หัวใจสำคัญคือ **อย่าแชร์หรือนำ Cache ไปรันต่อใน Job ที่มีสิทธิ์เขียน (Write Permissions)** ซึ่งในโครงสร้างของเรา ฝั่ง Deploy Job ไม่มีการดึง Cache ไปใช้งานเลย จึงปลอดภัยในจุดนี้

### 3.8 Quality Gates - ตรวจสอบคุณภาพด้วย fmt / clippy / test

```yaml
- name: Check formatting
  run: cargo fmt --all -- --check

- name: Clippy
  run: cargo clippy --workspace --target wasm32-unknown-unknown -- -D warnings

- name: Test
  run: cargo test --workspace
```

**ทำไมต้องใส่ไว้ใน Workflow ของการ Deploy** - เพื่อยึดกฎเหล็กข้อเดียวที่ชัดเจนว่า *"จะไม่มีโค้ดชุดไหนได้ขึ้น Production หากยังไม่ผ่านเกณฑ์คุณภาพทั้งหมด"* ซึ่งปลอดภัยกว่าการแยกไฟล์ CI และ Deploy ออกจากกัน ที่อาจเปิดช่องว่างให้เผลอ Deploy โค้ดที่ยังไม่ผ่านการทดสอบขึ้นไปได้

**ทำไม Clippy ต้องระบุ Target เป็น `wasm32` แทนที่จะเป็น Host** - โค้ดส่วนใหญ่ในเว็บ Leptos มักถูกครอบด้วยเงื่อนไข `#[cfg(target_arch = "wasm32")]` ซึ่งหากเรารัน Clippy บนสถาปัตยกรรม Host ของ Runner เพียงอย่างเดียว โค้ดส่วนนั้นจะไม่ถูกตรวจสอบเลย การระบุ Target เป็น `wasm32-unknown-unknown` จึงเป็นการสั่งให้ตรวจโค้ดที่จะถูกนำไปใช้งานจริงบนเบราว์เซอร์

**ทำไมต้องใส่แฟล็ก `-D warnings`** - แฟล็กนี้จะยกระดับคำเตือน (Warning) ทั้งหมดให้กลายเป็นข้อผิดพลาด (Error) เพื่อป้องกันไม่ให้มีข้อความประเภท *"เดี๋ยวค่อยกลับมาแก้ทีหลัง"* หลงเหลืออยู่ในระบบ

**ความเสี่ยงสำคัญที่ป้องกันไว้แล้ว** - โดยปกติ หาก Clippy อัปเดตเวอร์ชันใหม่อาจมี Lint กฎใหม่เพิ่มเข้ามา จนทำให้ CI พังข้ามคืนได้ทั้ง ๆ ที่เราไม่ได้แก้โค้ดเลย แต่ในโปรเจกต์นี้เราป้องกันไว้แล้วด้วยการ Pin เวอร์ชันของ Toolchain ใน `rust-toolchain.toml` จึงเป็นเหตุผลว่าทำไมเราถึง **ไม่ควรถอดการ Pin เวอร์ชันออกโดยเด็ดขาด**

**ความเสี่ยงเชิงกระบวนการ** - ตามที่ระบุในข้อ 3.1 ว่า Quality Gates ทั้งหมดจะทำงานหลังจาก Merge โค้ดแล้วเท่านั้น หากทีมเริ่มขยายใหญ่ขึ้น ควรแยก Workflow ออกมารันตรวจสอบตั้งแต่ตอนเปิด PR ด้วย

**ข้อแลกเปลี่ยนในการใช้งาน (Trade-off)** - หากโค้ดติดปัญหาแค่เรื่อง Lint เล็ก ๆ น้อย ๆ ก็จะส่งผลให้การ Deploy ถูกระงับทันที แม้ว่าการเปลี่ยนแปลงนั้นจะไม่ได้ส่งผลเสียต่อการทำงานของหน้าเว็บก็ตาม ซึ่งในที่นี้เราเลือกยอมแลกเพื่อรักษามาตรฐานและความสม่ำเสมอของโค้ดในระยะยาว

### 3.9 Supply Chain Security - สแกนช่องโหว่และ License ด้วย cargo-audit / cargo-deny

```yaml
- name: Install cargo-audit + cargo-deny
  uses: taiki-e/install-action@742a3317eac7bd62f91cd888b4eead5e784ba833 # v2.87.1
  with:
    tool: cargo-audit, cargo-deny

- name: Audit dependencies (RustSec advisory DB)
  run: cargo audit

- name: Deny check (advisories, licenses, bans)
  run: cargo deny check
```

**ทำไมต้องตรวจสอบ** - ในฝั่ง WebAssembly นั้น Dependency ทุกตัวจะถูกคอมไพล์รวมเข้าไปเป็นเนื้อเดียวกับไฟล์ `.wasm` ที่ส่งให้ผู้ใช้ดาวน์โหลด การตรวจสอบ Dependency จึงเปรียบเสมือนการตรวจความปลอดภัยของตัวผลงานโดยตรง อีกทั้งยังช่วยดักจับ License ที่ขัดแย้งกับสัญญาอนุญาตหลัก (เช่น MIT) ของโปรเจกต์ ก่อนที่จะถูกเผยแพร่ออกสู่สาธารณะ

**ความเสี่ยงและแนวทางรับมือ** - เมื่อฐานข้อมูล RustSec Advisory มีการรายงานช่องโหว่ใหม่เข้ามา อาจส่งผลให้ CI พังทันทีแม้เราจะไม่ได้แก้ไขโค้ดใด ๆ วิธีการแก้ไขชั่วคราวคือการใส่ `ignore` **พร้อมระบุเหตุผลประกอบอย่างชัดเจน** ลงในไฟล์ `deny.toml` และ `.cargo/audit.toml` 

อย่างไรก็ดี สิ่งที่ต้องระวังเป็นพิเศษคือ ทั้งสองไฟล์นี้จะต้องซิงก์ข้อมูลให้ตรงกัน และอย่าปล่อยให้การใส่ `ignore` กลายเป็นหลุมพรางถาวรโดยไม่มีใครกลับมาทบทวนหรืออัปเกรดเวอร์ชันของ Crate นั้น ๆ

**ความปลอดภัยของตัวติดตั้ง** - แม้กระทั่ง Action ที่ใช้สำหรับ *ติดตั้งเครื่องมือ* อย่าง `taiki-e/install-action` เราก็ต้อง Pin ด้วย Commit SHA เช่นเดียวกัน เพื่อป้องกันการโจมตีทาง Supply Chain ให้ครอบคลุมทุกจุด

### 3.10 Trunk Build - หัวใจหลักของ Leptos CSR

```yaml
- name: Install Trunk
  uses: jetli/trunk-action@1346cc09eace4beb84e403e199a471346d4684c9 # v0.5.1
  with:
    version: "v0.21.14"

- name: Build (release)
  # public-url is "/" for GitHub Pages org/user sites, or "/<repo>/" for project sites.
  run: trunk build --release --public-url /
```

**ทำไมต้อง Pin เวอร์ชันของ Trunk** - Trunk เป็น Build Tool ที่บางครั้งอาจมีการเปลี่ยนแปลงพฤติกรรมการ Build หรือขั้นตอนการรัน `wasm-opt` ข้ามเวอร์ชัน Minor การระบุเวอร์ชันเจาะจงไว้จะช่วยการันตีว่า ผลลัพธ์ของการ Build ในวันนี้จะยังคงเหมือนเดิมทุกประการ

**ข้อควรระวังเรื่อง `--public-url`** - ดังที่กล่าวไปในข้อ 2 นี่คือสาเหตุอันดับหนึ่งของอาการ "Deploy สำเร็จแต่เปิดมาเจอหน้าขาว" และจะเห็นว่ามีคอมเมนต์เตือนเรื่องนี้กำกับไว้ในไฟล์โดยตรง ซึ่งช่วยเตือนสติได้ดีมากเมื่อต้องกลับมาแก้ไขในอนาคต

**Hook สำคัญใน `Trunk.toml` ที่ห้ามลบเด็ดขาด**

```toml
[[hooks]]
stage = "pre_build"
command = "cargo"
command_arguments = ["build", "-q"]
```

เนื่องจากฟีเจอร์ `copy-file` ใน `Trunk.toml` (ที่ใช้คัดลอกไฟล์อย่าง `rss.xml`, `sitemap.xml`, `robots.txt`) จะทำงานแบบ**คู่ขนาน (Parallel)** ไปพร้อมกับ Rust Pipeline ทำให้ในการรันครั้งแรกบนเครื่อง Runner ที่เป็น Clean Checkout ไฟล์เหล่านี้จะยังไม่ได้ถูกสร้างขึ้นมา หากไม่มี Hook นี้ การ Build จะล้มเหลวทันทีเนื่องจากพยายามคัดลอกไฟล์ที่ยังไม่มีอยู่จริง ตัว Pre-build Hook นี้จึงทำหน้าที่บังคับให้ `build.rs` (ซึ่งเป็นตัวเขียนไฟล์เหล่านี้ขึ้นมา) ทำงานให้เสร็จเรียบร้อยก่อนเสมอ

**ความเสี่ยงเพิ่มเติม** - ขั้นตอนการรัน `wasm-opt` ของ Trunk อาจเกิดข้อผิดพลาดแบบเงียบ ๆ (Silent Failure) ได้ (ซึ่งเคยพบปัญหาทำนองนี้ในโปรเจกต์ Tauri + Leptos ที่เคยเขียนเล่าไว้ในบทความ `med-recon`) ขนาดไฟล์ `.wasm` หลัง Build อาจดูเรียบร้อยดีทั้งที่ความจริงยังไม่ได้ถูก Optimize หากสังเกตเห็นตัวเลขขนาดไฟล์เปลี่ยนไปอย่างผิดปกติ ให้ลองตรวจสอบการทำงานของ `wasm-opt` ในจุดนี้ก่อน

### 3.11 post_build - สร้างหน้า HTML ให้มีอยู่จริง เพื่อแก้ปัญหา 404 และ Open Graph (SEO)

```yaml
- name: Generate static per-post pages
  # Emit dist/post/<slug>/index.html for each post ... so /post/<slug> is a
  # real 200 page with per-post Open Graph tags instead of the 404.html fallback.
  run: cargo run --quiet --bin post_build
```

**ทำไมต้องมีขั้นตอนนี้** - เพราะ GitHub Pages จะเสิร์ฟหน้าเว็บเฉพาะไฟล์ที่มีอยู่จริงบน Disk เท่านั้น หากไม่มีไฟล์สำหรับเส้นทาง `/post/<slug>` คำขอจะตกไปที่ `404.html` ซึ่ง**ระบบจะส่งกลับไปด้วย HTTP Status Code 404 จริง ๆ** 

แม้ว่าผู้ใช้งานทั่วไปที่เปิดผ่านเบราว์เซอร์จะยังเข้าดูเว็บได้ (เพราะโค้ด JavaScript ของแอปแบบ SPA จะถูก Boot ขึ้นมาเพื่อทำ Client-Side Routing ต่อให้เอง) แต่สำหรับ Web Crawler หรือ Social Media Bot (เช่น Facebook, X หรือ Discord) พวกมันจะไม่รัน JavaScript ผลคือเมื่อเรานำลิงก์บทความไปแชร์ ภาพพรีวิว Open Graph (OG Card) จะไม่ขึ้น หรือได้แค่ภาพกลางของเว็บไซต์ไปแทน 

สคริปต์ `post_build` จึงเข้ามาแก้ปัญหานี้ โดยนำไฟล์ `dist/index.html` ที่ Build เสร็จแล้ว มาสร้างเป็นไฟล์ `dist/post/<slug>/index.html` แยกเป็นรายบทความ พร้อมทั้งแทนที่แท็ก `<title>`, Open Graph และ Twitter Card ให้ตรงตามเนื้อหาของแต่ละบทความ เพื่อให้ Crawler สามารถอ่านข้อมูลได้ด้วย HTTP 200 ทันที

**ข้อดีในเชิงสถาปัตยกรรม** - สคริปต์นี้ดึงข้อมูลบทความผ่าน Content Loader ตัวเดียวกับที่ตัวเว็บใช้งานจริง ทำให้ทั้ง Slug และ Metadata ต่าง ๆ ตรงกัน 100% เสมอ

**ข้อควรระวัง** - สคริปต์นี้จำเป็นต้องรัน **หลัง** ขั้นตอน `trunk build` เสมอ เพราะต้องรออ่านไฟล์ต้นฉบับจาก `dist/index.html` หากสลับลำดับ สคริปต์จะ Panic ทันที (ซึ่งถือเป็น Fail Loud ที่ดีกว่าปล่อยให้เงียบ) นอกจากนี้ ปัจจุบันระบบจะ Prerender เฉพาะหน้าบทความเท่านั้น ส่วนหน้าอื่น ๆ เช่น `/about` จะยังคงพึ่งพา 404 Fallback ตามปกติ

### 3.12 404.html - เตรียม SPA Fallback สำหรับ Client-Side Routing

```yaml
- name: Prepare SPA fallback (404.html)
  # Serve the app shell for unknown paths so client-side routing works.
  run: cp dist/index.html dist/404.html
```

**ทำหน้าที่อะไรและทำไมต้องมี** - แอปพลิเคชัน Leptos CSR จะจัดการเปลี่ยนหน้าผ่าน Client-Side Routing ในเบราว์เซอร์ เมื่อผู้ใช้กด Refresh หน้าเว็บขณะอยู่ที่ `/about` หรือ `/post/...` ตัวเซิร์ฟเวอร์ของ GitHub Pages จะหาไฟล์ที่ตรงกับ Path นั้นไม่พบ หากไม่มีไฟล์ `404.html` ผู้ใช้จะพบกับหน้า Error 404 ของ GitHub ทันที การคัดลอก `dist/index.html` มาเป็น `dist/404.html` จะช่วยให้ GitHub Pages ส่ง App Shell กลับมาให้เบราว์เซอร์ และปล่อยให้ Leptos Router ทำหน้าที่ดึงหน้าที่ถูกต้องขึ้นมาแสดงผลต่อได้

**ข้อจำกัดและความเสี่ยง**

- **อย่าพึ่งพา Fallback นี้กับหน้าสำคัญ**: เนื่องจากหน้า `404.html` จะถูกส่งกลับด้วยสถานะ HTTP 404 ส่งผลให้ **Search Engine จะไม่ทำการเก็บ Index** และ Crawler จะเห็นเฉพาะข้อมูล Meta Tag กลาง ๆ ของเว็บไซต์เท่านั้น (นี่จึงเป็นเหตุผลหลักว่าทำไมเราจึงต้องมีสคริปต์ `post_build` ในข้อ 3.11 สำหรับหน้าบทความ)
- **การตั้งชื่อไฟล์ผูกกับ `index.html` โดยตรง**: หากในอนาคตมีการเปลี่ยนชื่อ Entry Point ใน `Trunk.toml` จะต้องอย่าลืมมาอัปเดตคำสั่งคัดลอกไฟล์ใน Step นี้ให้ตรงกันด้วย

### 3.13 Upload Artifact - ส่งมอบไฟล์ข้าม Job อย่างเป็นระบบ

```yaml
- name: Upload artifact
  uses: actions/upload-pages-artifact@fc324d3547104276b827a68afc52ff2a11cc49c9 # v5.0.0
  with:
    path: dist
```

**ทำไมต้องทำแบบนี้** - เนื่องจาก Deploy Job จะทำงานแยกไปอยู่อีกเครื่อง Runner หนึ่งที่สะอาดและไม่มีไฟล์จาก Build Job หลงเหลืออยู่เลย การอัปโหลด Artifact จึงเปรียบเสมือนข้อตกลง (Contract) ในการส่งมอบชิ้นงานระหว่างสอง Job ทำให้ขั้นตอนการ Deploy เป็นไปอย่างเบ็ดเสร็จในครั้งเดียว (Atomic Deployment)

**ข้อกำหนดและข้อควรระวัง** - ภายใน Artifact จะต้องมีไฟล์ `index.html` อยู่ที่ Root ของ `path` เสมอ และขนาดรวมจะต้องไม่เกินข้อกำหนดของ GitHub Pages (เว็บไซต์ที่เผยแพร่ต้องมีขนาดไม่เกิน 1 GB) หากพบว่ามีไฟล์ที่ไม่เกี่ยวข้องหลุดเข้าไปในโฟลเดอร์ `dist/` ควรกลับไปแก้ไขที่ต้นทาง (เช่น ปรับแต่ง `.gitignore` หรือการตั้งค่าใน `Trunk.toml`) ดีกว่าการเขียนเงื่อนไข Exclude หลบไว้ที่ปลายทาง

### 3.14 Deploy Job - Job เดียวที่ถือสิทธิ์ในการเผยแพร่เว็บไซต์

```yaml
deploy:
  needs: build
  runs-on: ubuntu-latest
  permissions:
    pages: write
    id-token: write
  environment:
    name: github-pages
    url: ${{ steps.deployment.outputs.page_url }}
  steps:
    - name: Deploy to GitHub Pages
      id: deployment
      uses: actions/deploy-pages@cd2ce8fcbc39b97be8ca5fce6e763baed58fa128 # v5.0.0
```

**ทำไมต้องแยกเป็นอีกหนึ่ง Job ชัดเจน** - Job นี้จะ**ไม่มีการ Checkout โค้ด และไม่มีการรันคำสั่งใด ๆ ของตัวโปรเจกต์เลย** สิ่งที่ทำมีเพียงการเรียกใช้ Action `deploy-pages` เพื่อนำ Artifact ไปขึ้นระบบเท่านั้น หากโค้ดในโปรเจกต์หรือ Dependency มีการฝังโค้ดอันตราย ขอบเขตความเสียหายก็จะถูกจำกัดไว้แค่ใน Build Job ที่ไม่มีสิทธิ์เขียน นี่คือหลักการแบ่งแยกอำนาจและสิทธิ์ (Separation of Privileges) ที่ทำได้ง่าย ๆ ด้วย YAML เพียงไม่กี่บรรทัด

**ทำไมต้องใช้ `id-token: write` แทนที่จะใช้ Secret แบบดั้งเดิม** - Action `deploy-pages` จะทำการยืนยันตัวตนผ่าน OIDC (OpenID Connect) เพื่อขอ Token อายุสั้นมากจากระบบของ GitHub มายืนยันว่า *"ฉันคือ Workflow ของ Repo นี้จริง ๆ"* จึงไม่จำเป็นต้องสร้าง Personal Access Token (PAT) อายุยาวให้เสี่ยงต่อการหลุดหรือต้องคอยตาม Rotate อีกต่อไป

**ประโยชน์ของ `environment: github-pages`** - ช่วยให้ GitHub สามารถแสดงกล่องข้อมูล Deployment พร้อมลิงก์ URL ของเว็บไซต์บนหน้าหลักของ Repository ได้ และยังเปิดโอกาสให้เราตั้งค่า Protection Rules เพิ่มเติมได้ เช่น กำหนดให้ต้องมีผู้กดอนุมัติก่อนที่เว็บจะถูก Deploy (เหมาะสำหรับโปรเจกต์ระดับองค์กร)

**ความเสี่ยงและข้อจำกัด**

- หาก Workflow ถูกยกเลิกระหว่างที่กำลัง Deploy อยู่ (จากเงื่อนไข `concurrency` ในข้อ 3.3) อาจทำให้สถานะ Deployment ค้าง และส่งผลให้ Run ถัดไปเริ่มทำงานไม่ได้
- **ขีดจำกัดเวลา (Deployment Timeout)**: GitHub Pages มี Timeout สำหรับขั้นตอนการ Deploy อยู่ที่ 10 นาที (นับเฉพาะตอน Deploy ไม่รวมขั้นตอนการ Build) ซึ่งโดยทั่วไปจะใช้เวลาเพียงไม่กี่วินาที เว้นแต่ว่าขนาดของ Artifact จะใหญ่ผิดปกติ

**ทำไมเราถึงไม่ใช้ `actions/configure-pages`** - ใน Starter Workflow ทั่วไปของ GitHub มักจะมี Action ตัวนี้เพื่อช่วยคำนวณ Base URL อัตโนมัติ แต่ใน Workflow ของเราเลือกที่จะระบุค่า `--public-url` ในขั้นตอนการ Build โดยตรง เพื่อลดการพึ่งพา Third-party Actions ให้น้อยที่สุด (ลดความเสี่ยงด้าน Supply Chain) แลกกับการที่เราต้องใส่ใจระบุค่า Base URL ให้ถูกต้องด้วยตัวเอง

## 4. Risk Register - สรุปความเสี่ยงและมาตรการรับมือทั้งหมด

1. **ถูกแฮก Action หรือ Tag โดนชี้ไปที่อื่น**
    - จุดที่อาจเกิดขึ้น: ทุกคำสั่ง `uses:`
    - ผลกระทบหากเกิดขึ้น: โค้ดอันตรายถูกรันบน CI
    - แนวทางการป้องกันในโครงสร้างนี้: ล็อก (Pin) ด้วย Commit SHA ทุกตัว
    - สิ่งที่ยังต้องดูแลต่อ: ต้องคอยให้ Renovate หรือ Dependabot ช่วยส่ง PR อัปเดต SHA
2. **Token รั่วไหลจาก Dependency หรือ Script**
    - จุดที่อาจเกิดขึ้น: Build Job
    - ผลกระทบหากเกิดขึ้น: ผู้โจมตีขโมยสิทธิ์ Token ของรอบนั้นไปใช้
    - แนวทางการป้องกันในโครงสร้างนี้: จำกัดระดับ Workflow เป็น `contents: read`, ตั้ง `persist-credentials: false` และแยก Deploy Job ออกไปต่างหาก
    - สิ่งที่ยังต้องดูแลต่อ: ไม่มี
3. **ระบุ Path เผยแพร่เว็บผิดพลาด**
    - จุดที่อาจเกิดขึ้น: ค่า `--public-url`
    - ผลกระทบหากเกิดขึ้น: หน้าเว็บขาวโพลน / ไม่พบไฟล์ Asset (404)
    - แนวทางการป้องกันในโครงสร้างนี้: ใส่คอมเมนต์กำกับเตือนไว้ในไฟล์อย่างชัดเจน
    - สิ่งที่ยังต้องดูแลต่อ: ต้องเลือกค่าให้ตรงกับประเภทของ Repo ด้วยตัวเอง
4. **การเปิดหน้าเว็บตรง ๆ หรือ Refresh แล้วติด 404**
    - จุดที่อาจเกิดขึ้น: ฝั่ง Client-Side Routing
    - ผลกระทบหากเกิดขึ้น: แชร์ลิงก์แล้วการ์ดพรีวิวไม่ขึ้น และเสียผลลัพธ์ทาง SEO
    - แนวทางการป้องกันในโครงสร้างนี้: เตรียม `404.html` สำหรับ Fallback + สคริปต์ `post_build` ทำ Prerender รายบทความ
    - สิ่งที่ยังต้องดูแลต่อ: หน้าอื่น ๆ นอกเหนือจากบทความ (เช่น `/about`) ยังไม่ได้ทำ Prerender
5. **การ Deploy ทำงานชนกัน**
    - จุดที่อาจเกิดขึ้น: การ Push โค้ดติด ๆ กัน
    - ผลกระทบหากเกิดขึ้น: ลำดับการ Deploy สลับกัน / สถานะค้าง
    - แนวทางการป้องกันในโครงสร้างนี้: ใช้ `concurrency: pages`
    - สิ่งที่ยังต้องดูแลต่อ: หากตั้ง `cancel-in-progress: true` อาจทิ้งสถานะ Deployment ค้างได้ในบางกรณี
6. **Toolchain หรือกฎของ Lint เปลี่ยนไป**
    - จุดที่อาจเกิดขึ้น: Rust หรือ Clippy ออกเวอร์ชันใหม่
    - ผลกระทบหากเกิดขึ้น: CI พังข้ามคืนทั้งที่ไม่ได้แก้โค้ด / Local กับ CI รันได้ผลไม่ตรงกัน
    - แนวทางการป้องกันในโครงสร้างนี้: ล็อกเวอร์ชันตายตัวใน `rust-toolchain.toml`
    - สิ่งที่ยังต้องดูแลต่อ: ห้ามถอดการ Pin เวอร์ชันออกโดยเด็ดขาด
7. **มีรายงานช่องโหว่ความปลอดภัยใหม่**
    - จุดที่อาจเกิดขึ้น: การตรวจ `cargo audit` / `cargo deny`
    - ผลกระทบหากเกิดขึ้น: CI พังข้ามคืนจาก Advisory ใหม่
    - แนวทางการป้องกันในโครงสร้างนี้: ใส่เงื่อนไข `ignore` พร้อมระบุเหตุผลประกอบ
    - สิ่งที่ยังต้องดูแลต่อ: ต้องคอยซิงก์ไฟล์ `deny.toml` และ `audit.toml` ให้ตรงกันเสมอ
8. **ข้อมูลแคชตกค้างหรือเสียหาย**
    - จุดที่อาจเกิดขึ้น: Action `rust-cache`
    - ผลกระทบหากเกิดขึ้น: ในเครื่อง Local รันผ่าน แต่ CI กลับล้มเหลว
    - แนวทางการป้องกันในโครงสร้างนี้: จัดการสร้าง Cache Key ตาม Branch และ Lockfile
    - สิ่งที่ยังต้องดูแลต่อ: ต้องเข้าไปกดล้าง Cache ในระบบเป็นครั้งคราว
9. **Trunk คัดลอก Asset ก่อนที่ไฟล์จะถูกสร้าง**
    - จุดที่อาจเกิดขึ้น: ฟีเจอร์ `copy-file` ของ Trunk
    - ผลกระทบหากเกิดขึ้น: Build ล้มเหลวทันทีบน Clean Checkout
    - แนวทางการป้องกันในโครงสร้างนี้: บังคับลำดับด้วย Pre-build Hook ให้รัน `cargo build -q` ก่อน
    - สิ่งที่ยังต้องดูแลต่อ: ไม่มี
10. **ติดเพดานข้อจำกัดของ GitHub Pages**
    - จุดที่อาจเกิดขึ้น: ตัวบริการ Pages
    - ผลกระทบหากเกิดขึ้น: ไซต์ต้องมีขนาดไม่เกิน 1 GB, แบนด์วิดท์ไม่เกิน 100 GB/เดือน และ Deploy ต้องจบภายใน 10 นาที
    - แนวทางการป้องกันในโครงสร้างนี้: ไซต์นี้เป็นแบบ Static ขนาดเล็กจึงไม่เกินเพดาน
    - สิ่งที่ยังต้องดูแลต่อ: โควตา 10 Builds/ชม. ไม่นับรวมกับ Workflow แบบ GitHub Actions
11. **ไม่มีระบบ Rollback อัตโนมัติในตัว**
    - จุดที่อาจเกิดขึ้น: ตัวบริการ Pages
    - ผลกระทบหากเกิดขึ้น: ต้องย้อนกลับเวอร์ชันเมื่อเกิดปัญหา
    - แนวทางการป้องกันในโครงสร้างนี้: สั่ง `git revert` แล้ว Push โค้ดขึ้นไปใหม่
    - สิ่งที่ยังต้องดูแลต่อ: ไม่มี Downtime เนื่องจาก Pages จะแสดงเวอร์ชันเดิมไว้จนกว่าการ Deploy ใหม่จะสำเร็จ

## 5. Checklist ก่อน Push โค้ดหรือก่อนปรับแก้ Workflow

- [ ] ตั้งค่า Pages Source เป็น **GitHub Actions** ใน Settings ของ Repository เรียบร้อยแล้ว
- [ ] ตรวจสอบว่าค่า `--public-url` สอดคล้องกับประเภทของ Repo (User Site ใช้ `/`, Project Site ใช้ `/<repo>/`)
- [ ] ไฟล์ `rust-toolchain.toml` มีการระบุ Target `wasm32-unknown-unknown` รวมถึง Component `rustfmt` และ `clippy` ไว้อย่างครบถ้วน
- [ ] ไฟล์ `Cargo.lock` ถูก Commit ขึ้น Git เสมอ และโฟลเดอร์ `dist/` อยู่ใน `.gitignore`
- [ ] ทดสอบ Build บนเครื่อง Local ด้วยคำสั่ง: `trunk build --release --public-url <ค่าเดียวกับบน CI>` แล้วลองเปิดดูไฟล์ใน `dist/` ว่าโหลด Asset ครบถ้วน
- [ ] หากมีการเพิ่มหรือสลับขั้นตอนใน Workflow ให้ตรวจเช็กลำดับเสมอ: `trunk build` → `post_build` → `cp 404.html` → `upload artifact`
- [ ] Action ใหม่ทุกตัวต้อง Pin ด้วย Commit SHA เสมอ พร้อมใส่คอมเมนต์ระบุเวอร์ชันกำกับไว้
- [ ] เปิดใช้งาน Branch Protection โดยตั้งให้ Job `build` เป็น Required Status Check ก่อนจะยอมให้ Merge โค้ด

## 6. ปัญหาที่พบบ่อยและแนวทางแก้ไข (Troubleshooting)

- **หน้าเว็บขาวโพลน / Console ฟ้อง 404 ไม่พบไฟล์ `.wasm`**
  - สาเหตุที่พบบ่อย: ค่า `--public-url` ไม่ตรงกับประเภทของ Repo
  - จุดที่ต้องไปตรวจสอบและแก้ไข: ดูหัวข้อ 2 และตรวจสอบคำสั่ง `trunk build`
- **กด Refresh หน้า `/post/...` หรือ `/about` แล้วติด 404**
  - สาเหตุที่พบบ่อย: ไม่มีไฟล์ `404.html` หรือขั้นตอนการ Deploy ยังไม่เสร็จสมบูรณ์
  - จุดที่ต้องไปตรวจสอบและแก้ไข: ตรวจสอบขั้นตอน 3.12 และดูประวัติการ Deploy ล่าสุด
- **แชร์ลิงก์บทความแล้วรูปพรีวิวหรือการ์ด OG ไม่แสดงผล**
  - สาเหตุที่พบบ่อย: สคริปต์ `post_build` ไม่ได้ทำงาน หรือถูกรันก่อนขั้นตอน `trunk build`
  - จุดที่ต้องไปตรวจสอบและแก้ไข: ตรวจสอบลำดับขั้นตอนใน 3.11
- **Deploy Job ล้มเหลวพร้อมข้อความ *"deployment in progress"***
  - สาเหตุที่พบบ่อย: Run ก่อนหน้าถูกสั่งยกเลิกระหว่างทาง ทำให้สถานะ Deploy ค้าง
  - จุดที่ต้องไปตรวจสอบและแก้ไข: ปรับค่าเป็น `cancel-in-progress: false` แล้วสั่ง Re-run ใหม่ (ดูหัวข้อ 3.3)
- **Deploy Job ล้มเหลวด้วยข้อผิดพลาดเรื่องสิทธิ์ (Permission Denied)**
  - สาเหตุที่พบบ่อย: ยังไม่ได้สลับ Pages Source เป็น Actions หรือกำหนด `permissions` ไม่ครบ
  - จุดที่ต้องไปตรวจสอบและแก้ไข: ตรวจสอบการตั้งค่าใน Pages Settings และดูหัวข้อ 3.14
- **CI พังเพราะ Clippy แจ้งเตือน ทั้ง ๆ ที่ไม่ได้แก้ไขโค้ดเลย**
  - สาเหตุที่พบบ่อย: เคยถอดการ Pin เวอร์ชันของ Toolchain ออก หรือเวอร์ชันของ Rust หลุด
  - จุดที่ต้องไปตรวจสอบและแก้ไข: ตรวจสอบไฟล์ `rust-toolchain.toml` และอย่าถอดการ Pin เวอร์ชัน
- **ขั้นตอน `cargo audit` หรือ `cargo deny` รันไม่ผ่าน**
  - สาเหตุที่พบบ่อย: มีการรายงานช่องโหว่ความปลอดภัยใหม่ใน RustSec Advisory
  - จุดที่ต้องไปตรวจสอบและแก้ไข: ใส่เงื่อนไข `ignore` พร้อมระบุเหตุผลใน `deny.toml` และ `.cargo/audit.toml` หรืออัปเดต Dependency
- **ในเครื่อง Local รันผ่าน แต่บน CI พังแบบไม่มีเหตุผล**
  - สาเหตุที่พบบ่อย: แคชบน CI ตกค้าง/เสียหาย หรือคอมไพเลอร์ Rust คนละเวอร์ชัน
  - จุดที่ต้องไปตรวจสอบและแก้ไข: สั่งลบ Cache ในหน้า Actions และตรวจเช็กเวอร์ชันของ `rustc` กับ `trunk` ให้ตรงกัน

## 7. ปรับใช้กับโปรเจกต์ Leptos อื่น (โครงสร้างเริ่มต้นแบบขั้นต่ำ)

หากต้องการนำโครงสร้างนี้ไปปรับใช้กับโปรเจกต์ Leptos CSR อื่น ๆ สามารถสร้างไฟล์ `.github/workflows/deploy.yml` แล้วคัดลอกโครงร่างขั้นต่ำด้านล่างนี้ไปใช้งานได้เลย โดยให้แทนที่ `<SHA>` ด้วย Commit SHA จริงของแต่ละ Action (สามารถตรวจสอบ SHA ล่าสุดได้จากหน้า Releases ของแต่ละ Action ครับ)

```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: pages
  cancel-in-progress: false   # ให้ deploy ที่กำลังทำอยู่ทำงานจนจบก่อน

jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@<SHA>
        with:
          persist-credentials: false

      - uses: dtolnay/rust-toolchain@<SHA>
        with:
          targets: wasm32-unknown-unknown

      - uses: Swatinem/rust-cache@<SHA>

      - run: cargo fmt --all -- --check
      - run: cargo clippy --target wasm32-unknown-unknown -- -D warnings
      - run: cargo test --workspace

      - uses: jetli/trunk-action@<SHA>
        with:
          version: "v0.21.14"

      # หากเป็น Project Site ให้เปลี่ยน / เป็น /<repo>/
      - run: trunk build --release --public-url /

      - run: cp dist/index.html dist/404.html

      - uses: actions/upload-pages-artifact@<SHA>
        with:
          path: dist

  deploy:
    needs: build
    runs-on: ubuntu-24.04
    permissions:
      pages: write
      id-token: write
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/deploy-pages@<SHA>
        id: deployment
```

**ส่วนประกอบเพิ่มเติมที่แนะนำให้เพิ่มเข้ามาเมื่อโปรเจกต์เริ่มจริงจังมากขึ้น:**
- ไฟล์ `rust-toolchain.toml` เพื่อล็อกเวอร์ชัน Rust ให้ตรงกันอย่างแน่นอนระหว่างเครื่อง Dev และ CI
- ด่านตรวจความปลอดภัยและ License ด้วย `cargo-audit` และ `cargo-deny`
- สคริปต์ `post_build` สำหรับทำ Prerender หน้าบทความ หากโปรเจกต์มีหน้าที่จำเป็นต้องแชร์ลง Social Media หรือต้องการผลลัพธ์ทาง SEO

## 8. บทสรุป

หากมองภาพรวมแล้ว แนวคิดเบื้องหลังไฟล์ `deploy.yml` ของ rust-blog สามารถสรุปออกมาได้เป็น 3 เลเยอร์สำคัญ:

1. **เลเยอร์แห่งความแน่นอน (Reliability)** - การล็อก (Pin) ทุกสิ่งที่เปลี่ยนแปลงได้ให้อยู่กับที่ ทั้ง Commit SHA ของ Action, เวอร์ชันของ Rust Toolchain, เวอร์ชันของ Trunk ไปจนถึงการจัดการ Cache Key เพื่อให้มั่นใจว่า ในวันที่ CI พัง จะต้องพังเพราะโค้ดที่เราแก้ไขจริง ๆ ไม่ใช่เพราะสภาพแวดล้อมภายนอกเปลี่ยนแปลงไปเอง
2. **เลเยอร์แห่งความปลอดภัย (Security)** - ยึดหลักสิทธิ์น้อยที่สุด (Least Privilege) โดยแยก Job ตามความรับผิดชอบอย่างชัดเจน ไม่ใช้ Long-lived Secrets และไม่เปิดโอกาสให้ Job ที่ถือสิทธิ์ Deploy เข้าไปสัมผัสกับโค้ดของโปรเจกต์ ซึ่งถือเป็นแนวทางป้องกันที่คุ้มค่ามาก
3. **เลเยอร์เพื่อการทำงานจริงบน GitHub Pages** - ทำความเข้าใจข้อจำกัดของระบบ Static Hosting ที่ไม่มี Server Backend และ Crawler ไม่รัน JavaScript ดังนั้นหน้าเว็บที่ต้องการผลด้าน SEO และการแชร์ลิงก์จึงต้องสร้างเป็นไฟล์ HTML จริง ๆ เตรียมไว้เสมอ รวมถึงต้องระบุ Base Path ให้สอดคล้องกับ URL ของ Repository

ในอนาคต หากคุณกลับมาที่บทความนี้เพราะ CI กำลังฟ้องตัวแดง แนะนำให้เริ่มตรวจเช็กจากรายการความเสี่ยงใน **ข้อ 4** และแนวทางแก้ไขปัญหาใน **ข้อ 6** ก่อนเป็นอันดับแรกครับ แล้วคำถามที่ว่า *"ทำไมจู่ ๆ มันถึงพัง?"* จะเปลี่ยนเป็น *"อ๋อ สาเหตุเกิดจากข้อนี้นี่เอง"* ได้รวดเร็วขึ้นอย่างแน่นอนครับ
