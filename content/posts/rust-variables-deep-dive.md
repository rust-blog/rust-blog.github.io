## ชั้น 1: ภาพกว้าง ตัวแปรคืออะไรใน 1 นาที

```rust
let x = 5;
```

ขอเริ่มแบบนี้ ให้จินตนาการว่า `let x = 5;` เหมือนการเขียนป้ายชื่อ **"x"** แล้วติดบนกล่องที่ใส่ค่า `5` อยู่ พอนึกออกไหมครับ

กฎของ Rust มีอยู่ว่า **กล่องที่ติดป้ายไว้โดยไม่ได้เขียนว่า "แก้ได้" จะเปิดเปลี่ยนของข้างในไม่ได้เด็ดขาด** ถ้าอยากแก้ได้ต้องติดป้ายให้ชัดเจนตั้งแต่แรก ลองดูตัวอย่างนี้

```rust
let mut x = 5; // ป้ายนี้บอกว่า "แก้ได้"
x = 6;         // ✓ ผ่าน
```

ถ้าไม่ใส่ `mut` แล้วพยายามแก้ค่า คอมไพเลอร์จะไม่ยอมคอมไพล์ตั้งแต่แรก

```rust
let x = 5;
x = 6; // ❌ error[E0384]: cannot assign twice to immutable variable
```

ถ้ารีบ บทความจบแค่นี้ก็พอครับ แต่ถ้าอยากรู้ว่า **ทำไม** Rust ถึงบังคับแบบนี้ อ่านชั้น 2 ต่อได้เลย มาสิๆ

> 💡 **ทำไมถึงต้อง "แก้ไม่ได้" โดยค่าเริ่มต้น?**
> เพราะบั๊กส่วนใหญ่ที่กวนใจคนเขียนโค้ดคือเผลอเปลี่ยนค่าที่ไม่ควรเปลี่ยน ยิ่งโค้ดยาวเท่าไหร่ ยิ่งยากที่จะเจอ Rust เลยย้ายการค้นหาบั๊กแบบนี้ มาอยู่ที่ตอนคอมไพล์เลย ผิดก็ไม่ทันได้รัน เฟลซะก่อน

## ชั้น 2: กลไกจริง binding, scope, shadowing

### 2.1 "binding" ไม่ใช่ "ตัวแปร" ตามที่เราเคยรู้จัก

ในภาษา C หรือ JavaScript `ตัวแปร` แปลว่า **ตำแหน่งในหน่วยความจำ** ที่เก็บค่าได้ `int x` คือจองพื้นที่ 4 ไบต์ แล้วตั้งชื่อว่า `x`

แต่ใน Rust `let x = 5;` เราเรียกว่า **binding** แปลตรงตัวว่า "การผูก" มันคือการผูก**ชื่อ** `x` เข้ากับ**ค่า** `5`

ความต่างนี้สำคัญมาก เพราะ binding เป็นแนวคิด**ระดับโค้ด** ไม่ใช่ระดับหน่วยความจำ ถ้าสงสัยอ่านต่อครับ

```rust
let x = 5;
let y = x * 2; // คอมไพเลอร์อาจคำนวณ y = 10 ล่วงหน้าได้เลย ไม่ต้องมีพื้นที่เก็บจริง
```

คอมไพเลอร์เป็นคนตัดสินใจเองว่าค่า `x` จะไปอยู่ที่ไหน เก็บใน stack เก็บใน register ของ CPU หรือหายไปเลยเพราะคำนวณล่วงหน้าแล้ว (constant folding) เราสั่งไม่ได้ และไม่ต้องสนใจด้วย นี่คือสิ่งที่เรียกว่า "ให้ compiler จัดการ ส่วนเราจัดการ logic"

> 💡 **ทำไมต้องแยก "ชื่อ" ออกจาก "ที่อยู่"?**
> ถ้า binding คือที่อยู่จริง (แบบ C) ตัว optimizer จะเคลื่อนย้าย/จัดเรียงค่าไม่ได้ เพราะทุกคนมองเห็นที่อยู่ ถ้า binding เป็นแค่ชื่อ คอมไพเลอร์มีอิสระเต็มที่ในการจัดวาง คุณได้ความเร็วของ C โดยไม่ต้องจ่ายด้วยการคิดเองเรื่อง memory layout

### 2.2 ทำไม immutable by default? มี 4 เหตุผลเรียงตามความสำคัญ ดังนี้

**1. ป้องกันเผลอเปลี่ยนตั้งแต่ตอนคอมไพล์**

บั๊กจากการเปลี่ยนค่าที่ไม่ตั้งใจจะเปลี่ยนนั้นเป็นบั๊กที่พบได้บ่อยที่สุดในภาษา mutable ทั้งหมด (C, C++, JS, Python ...) และตรวจจับยากมากในโค้ดใหญ่ ๆ ภาษาเหล่านั้นไม่มีทางรู้ว่าคุณตั้งใจหรือเผลอเลย

Rust จึงตอบเราว่า *"ไม่รู้ก็ไม่ต้องเดา ห้ามแก้ถ้าไม่ได้ประกาศไว้ล่วงหน้า"* ผิดตอนคอมไพล์ไปเลย ใจๆ

นี่คือ **ข้อความ error จริง** (ทดสอบด้วย rustc 1.98) เมื่อลองรันโค้ด `let x = 5; x = 6;`

```text
error[E0384]: cannot assign twice to immutable variable `x`
 --> main.rs:3:5
  |
2 |     let x = 5;
  |         - first assignment to `x`
3 |     x = 6;
  |     ^^^^^ cannot assign twice to immutable variable
  |
help: consider making this binding mutable
  |
2 |     let mut x = 5;
  |         +++
```

สังเกตว่าคอมไพเลอร์**ไม่ได้แค่ด่า** แต่ชี้บรรทัดที่ประกาศครั้งแรก และแนะนำคำตอบให้ด้วย (ใส่ `mut` ที่ไหน) เพราะมันรู้ว่าคุณอาจตั้งใจจริงๆ แค่ลืมประกาศ

**2. อ่านโค้ดแล้วรู้ได้ทันทีว่าอะไรเปลี่ยนได้**

```rust
let config = load_config();   // ไม่มีใครแก้ config ได้อีกแล้ว อ่านต่อได้เลย ไม่ต้องกลัว
let mut counter = 0;          // มีที่เดียวในฟังก์ชันนี้ที่เปลี่ยนค่าได้
```

เวลา Review โค้ด 1,000 บรรทัด คุณไม่ต้องไล่หา `counter += 1` ทุกบรรทัด Rust บอกให้รู้ตั้งแต่บรรทัดประกาศว่าเจ้านี่เปลี่ยนได้นะ

**3. ง่ายต่อการให้เหตุผล (local reasoning)**

ถ้า binding แก้ค่าไม่ได้ ค่าของมัน ณ จุดใดก็ตามในโค้ด = ค่าตอนประกาศเท่านั้น (หรือค่าที่ shadow ไว้ เดี๋ยวอ่านในข้อ 2.4) คุณไม่ต้องจำ state ว่าตอนนี้ `x` เป็นเท่าไหร่แล้ว

**4. ปูทางให้ concurrency**

immutable ค่าเดียว ไม่มีทางเกิด data race (สองเธรดแก้ค่าเดียวกันพร้อมกัน) แต่ต้องบอกตามตรงว่า ตัวที่ป้องกัน data race จริงๆ คือระบบ **ownership + borrowing** (อ่านเรื่องนี้ต่อใน The Book บทที่ 4 นะครับ) ส่วน "immutable by default" เป็นตัวช่วยเสริมอีกชั้นหนึ่งครับ

### 2.3 ทำไมต้องพิมพ์ `mut` เอง?

บางคนบ่นว่า "ภาษา C ไม่ต้องพิมพ์ `mut` ก็แก้ค่าได้เลย ทำไม Rust ยุ่งยากจัง" นั่นสิ 

คำตอบอยู่ที่ **ต้นทุนของการอ่านโค้ด**

| | C / JavaScript | Rust |
| --- | --- | --- |
| เขียน | `int x = 5; x = 6;` (ไม่ต้องประกาศเจตนา) | `let mut x = 5; x = 6;` |
| อ่านโค้ด 1,000 บรรทัด | ต้องไล่หาเองว่าตรงไหนเปลี่ยนค่า | เห็น `mut` ปุ๊บ รู้เลยว่าตรงนี้เปลี่ยนได้ |
| เผลอเปลี่ยนค่าที่ไม่ตั้งใจ | รันแล้ว bug | คอมไพล์ไม่ผ่านเลย |
| งาน review | บรรทัดนี้ตั้งใจไหม? | คำถามนั้นไม่เกิด |

สรุปคือ Rust บังคับให้คุณ **ประกาศความตั้งใจ** ก่อน แลกกับการที่คนอื่น (รวมถึงตัวคุณเองในอีก 6 เดือน) อ่านโค้ดได้เร็วและปลอดภัยขึ้นอย่างมาก

### 2.4 scope ตัวแปร "ตาย" ตอนไหน?

ทุก binding เกิดใน **scope** (block `{}`) จะตายเมื่อ scope จบ

```rust
fn main() {
    let outer = 1;        // outer เกิดที่นี่
    {
        let inner = 2;    // inner เกิดที่นี่
        println!("{inner}"); // ✓ ใช้ได้
    }                     // ← inner ตายตรงนี้ (คืนหน่วยความจำทันที)
    println!("{inner}");  // ❌ error[E0425]: cannot find value `inner`
}                         // ← outer ตายตรงนี้
```

error จริงที่ได้ (rustc 1.98)

```text
error[E0425]: cannot find value `inner` in this scope
 --> main.rs:7:16
  |
7 |     println!("{inner}");
  |                ^^^^^
  |
help: the binding `inner` is available in a different scope in the same function
 --> main.rs:4:13
  |
4 |         let inner = 2;
  |             ^^^^^
```

เห็นไหมว่าคอมไพเลอร์**เห็นว่า binding นั้นยังมีชีวิตอยู่** แค่หลุด scope ไป มันชี้ให้เห็นว่ามันอยู่บรรทัดไหนของ scope ไหน แล้วให้คุณตัดสินใจเอง

จุดที่ Rust ต่างจากภาษาที่มีตัวเก็บขยะ (GC) อย่าง Java/Go/JS คือ **ตัวแปรตายแบบกำหนดเวลาได้เป๊ะๆ** ไม่มีเดี๋ยว GC ค่อยเก็บทีหลังตอนไม่รู้ตัว เพราะระบบ **RAII** (Resource Acquisition Is Initialization) ของที่ binding ถืออยู่ (ไฟล์, connection, หน่วยความจำ) ถูกคืน**ทันที**ที่ scope จบ

> 💡 **ทำไมต้องตายทันทีที่จบ scope?**
> ถ้าของยังไม่ถูกคืนจนกว่าจะ "ไม่รู้เมื่อไหร่" (แบบ GC) คุณจะควบคุมได้แย่ลง ไฟล์อาจยังเปิดค้าง, หน่วยความจำอาจพุ่งก่อน GC ทำงาน Rust เลือก "คืนแน่นอน ทันทีที่ประกาศจบ" เป็นพฤติกรรมที่พยากรณ์ได้ 100% และ**ไม่ต้องมี garbage collector** เลย

### 2.5 shadowing ตัวที่คนเข้าใจผิดมากที่สุด

ดูโค้ดนี้นะครับ

```rust
let x = 5;
let x = x + 1; // binding ใหม่ ชื่อ x อีกตัวหนึ่ง
let x = x * 2; // binding ใหม่อีกตัวหนึ่ง
println!("{x}"); // 12
```

นี่คือ **shadowing** มันสร้าง binding ใหม่มาบังชื่อเก่า สิ่งที่ควรรู้ให้ลึกไปกว่านั้นคือ

- ของเก่า**ยังอยู่**ในหน่วยความจำ จนกว่าจะจบ scope แค่ใช้ชื่อไม่ได้แล้ว (ชื่อถูกบัง)
- ต่างจาก `mut` โดยสิ้นเชิงเพราะ `mut` แก้**กล่องเดิม**, shadow สร้าง**กล่องใหม่**

แล้วทำไมต้องมีทั้งสอง? เพราะมันใช้ต่างสถานการณ์กันยังไงล่ะ

```rust
// ใช้ mut แก้ค่าของเดิมจริงๆ (เช่นนับถอยหลัง)
let mut countdown = 3;
while countdown > 0 {
    println!("{countdown}");
    countdown -= 1;
}

// ใช้ shadow: "รีไฟน์" ค่าค่อยเป็นค่อยไป โดยไม่ต้องเปิดให้แก้
let input = String::from("  42  ");
let input = input.trim();          // เปลี่ยน type จาก String เป็น &str
let input = input.parse::<i32>();  // เปลี่ยนเป็น Result<i32, _>
```

เห็นไหมครับว่า shadow ช่วยให้**เปลี่ยน type ระหว่างทาง**ได้ด้วย (`String` → `&str` → `i32`) แต่!!! `mut` ทำแบบนี้ไม่ได้นะ เพราะ type ของ binding ตายตัวตั้งแต่ประกาศ 

> 💡 **ทำไม Rust ถึงมี shadowing ทั้งที่ดูเหมือนเปลี่ยนค่าหลอกๆ?**
> มันคือสไตล์ **functional** ข้อมูลไหลจาก binding หนึ่งสู่อีก binding หนึ่ง ไม่มีที่เดียวที่ถูกแก้ซ้ำไปมา เหมือนการเขียนค่าใหม่ลงบนกระดาษแผ่นใหม่ทุกครั้ง แทนที่จะขีดฆ่าแก้บนแผ่นเดิม คอมไพเลอร์ไม่เคยสับสน เพราะ binding เก่า/ใหม่เป็นคนละตัวกันชัดเจน เจ๋งไหมล่ะ

## ชั้น 3: ลงลึกสุด เกิดอะไรขึ้นในหน่วยความจำจริง (จะมีใครอ่านถึงชั้นนี้ไหมน้อ)

### 3.1 ค่าเล็กๆ ที่อยู่บน stack

**stack** คือพื้นที่หน่วยความจำที่เรียงเป็นชั้นๆ (LIFO) มันเร็วมาก เพราะเพิ่ม/ลดขนาดแค่ขยับตัวชี้ 1 ครั้ง

เมื่อ `main()` รัน ระบบจะสร้าง **stack frame** ของมัน แล้ววาง binding ลงไป

| binding | type | ขนาดจริง (64-bit) | ตำแหน่ง |
| ------- | ---- | ----------------- | ------- |
| `x` | `u8` | 1 ไบต์ | stack frame ของ `main` |
| `y` | `f64` | 8 ไบต์ | stack frame ของ `main` |
| `z` | `String` | 24 ไบต์ | stack frame ของ `main` (ชี้ไป heap) |

ลองด้วยตัวเองได้ มาถึงชั้นนี้จะอ่านอย่างเดียวไม่ได้นะ คุณครูตีมือเลย

```rust
println!("u8:     {}", std::mem::size_of::<u8>());
println!("i32:    {}", std::mem::size_of::<i32>());
println!("f64:    {}", std::mem::size_of::<f64>());
println!("usize:  {}", std::mem::size_of::<usize>());
println!("String: {}", std::mem::size_of::<String>());
```

ผลลัพธ์จริงบนเครื่อง 64-bit (rustc 1.98)

```text
u8:     1
i32:    4
f64:    8
usize:  8
String: 24
```

`String` ใช้ 24 ไบต์ = `ptr` (8) + `len` (8) + `capacity` (8)  ตัวเลขที่เคยเห็นในตารางข้างบน เอาเข้าจริงเป็นแบบนี้ [ดูได้จาก std docs](https://doc.rust-lang.org/std/mem/fn.size_of.html)

ทุกครั้งที่ scope จบ → stack frame ถูก pop ออก → ตัวแปร "ตาย" ตามข้อ 2.4 นี่คือกลไกที่แท้จริงของ deterministic drop

### 3.2 ค่าใหญ่ๆ อยู่บน heap นะ stack เก็บแค่ใบสั่ง

`String` ยาว 10 ตัวอักษร ใส่ใน 10 ไบต์ใน stack ไม่ได้ เพราะความยาวไม่รู้ตอนคอมไพล์ จึงไปอยู่ **heap** (พื้นที่ที่จองได้แบบไดนามิก) ส่วน stack เก็บแค่ **3 ตัวเลขชี้พิกัด**

```
stack (24 bytes)                heap
┌───────────────┐               ┌──────────────────────┐
│ ptr ──────────┼──────────────►│ "สวัสดี" (18B)         │
│ len = 18      │               └──────────────────────┘
│ capacity = 18 │
└───────────────┘
```

- `ptr` คือที่อยู่บน heap ที่ข้อมูลอยู่จริง
- `len` คือจำนวนไบต์ที่ใช้
- `capacity` คือจำนวนไบต์ที่จองไว้

**หลักฐานจริง** รันโค้ดนี้ดูนะ

```rust
fn main() {
    let s = String::from("สวัสดี");
    println!("ptr:      {:p}", s.as_ptr());
    println!("len:      {}", s.len());
    println!("capacity: {}", s.capacity());
    println!("bytes:    {:?}", s.as_bytes());
}
```

ได้ผลลัพธ์:

```text
ptr:      0x13b0e966310   ← ที่อยู่บน heap (ข้อมูลอยู่จริง)
len:      18              ← "สวัสดี" = 6 ตัวอักษร × 3 ไบต์ (UTF-8)
capacity: 18
bytes:    [224, 184, 170, 224, 184, 167, ...]
```

และถ้าอยากเห็น "stack กับ heap อยู่คนละโซน" ให้ลองพิมพ์ที่อยู่ทั้งสองแบบ

```rust
fn main() {
    let x = 5;
    let s = String::from("hi");
    println!("x  (stack): {:p}", &x);
    println!("s  (stack): {:p}", &s);
    println!("heap buf :  {:p}", s.as_ptr());
}
```

```text
x  (stack): 0x49807ef8fc
s  (stack): 0x49807ef8e0   ← อยู่ใกล้กัน (บน stack เดียวกัน)
heap buf :  0x1ae0612f570  ← ไกลคนละโลกเลย (บน heap)
```

> 📌 ที่อยู่จริงจะ**เปลี่ยนทุกครั้งที่รัน** (ระบบกันการโจมตีแบบ ASLR) แต่รูปแบบจะเหมือนเดิมเสมอ สิ่งที่อยู่บน stack อยู่ติดกัน ส่วน heap อยู่คนละโซน ดูที่ "ความห่าง" ไม่ใช่ตัวเลขนะครับ

เมื่อ binding `String` ตาย → Rust เรียก `drop` → คืน 18 ไบต์บน heap ทันที ต่างจาก GC ที่ "ไม่รู้เมื่อไหร่จะเก็บ" 

> 💡 **ทำไมต้องมี len และ capacity แยกกัน?**
> เวลา `push` ข้อมูลเพิ่ม ถ้า `len < capacity` เติมในที่เดิมได้เลย ไม่ต้องย้ายข้อมูล แต่ถ้าเต็ม ค่อยจองที่ใหม่ แล้วย้ายทั้งก้อน ลองรันดูจริงๆ ว่า capacity มันโตยังไง
>
> ```rust
> let mut v = Vec::new();
> for i in 0..=16 {
>     println!("len = {i:2}, capacity = {}", v.capacity());
>     v.push(i);
> }
> ```
>
> ```text
> len =  0, capacity = 0
> len =  1, capacity = 4
> len =  4, capacity = 4
> len =  5, capacity = 8     ← เต็มแล้ว ต้องขยาย
> len =  8, capacity = 8
> len =  9, capacity = 16    ← ขยายอีกที (เท่าตัว)
> len = 16, capacity = 16
> len = 17, capacity = 32
> ```
>
> capacity โตแบบ**เท่าตัว** (4 → 8 → 16 → 32) คือยอมเสียหน่วยความจำนิดหน่อย แลกกับการไม่ต้องย้ายข้อมูลบ่อยๆ ค่าเฉลี่ยของการ push จึงเป็น O(1) [ที่มา: `Vec` docs](https://doc.rust-lang.org/std/vec/struct.Vec.html)

### 3.3 ความจริงที่คนส่วนใหญ่ไม่รู้ binding ไม่ได้อยู่ใน memory เสมอไป

กลับไปที่ข้อ 2.1 ครับ คอมไพเลอร์มีอิสระเต็มที่ ลองพิจารณาโค้ดนี้ดู

```rust
use std::hint::black_box;

#[inline(never)]
fn compute(x: i32) -> i32 {
    let y = x + 1; // binding y จะไปอยู่ที่ไหน?
    y
}

fn main() {
    black_box(compute(5));
}
```

`black_box` คือฟังก์ชันที่บอกคอมไพเลอร์ว่า *"ทำเป็นมองไม่เห็น optimization นะ"*  ใช้บังคับให้โค้ดเรารันจริง ไม่งั้นคอมไพเลอร์อาจลบทิ้งทั้งฟังก์ชัน

คอมไพล์ด้วย `rustc -O --emit=asm main.rs` แล้วเปิดไฟล์ assembly ที่ได้ (ทดสอบบน Windows x64, rustc 1.98 ส่วน `; ←` เป็นคอมเมนต์ที่ผมเติมเองเพื่ออธิบาย)

```asm
main:
	pushq	%rax
	movl	$6, 4(%rsp)      ; ← นี่คือทั้งหมดที่เหลือของ compute(5): เลข 6
	leaq	4(%rsp), %rax
	#APP                   ; ← ส่วน black_box (บังคับให้ค่าอยู่ใน memory)
	#NO_APP
	popq	%rax
	retq
```

อ่าน assembly นี้ให้เห็นเรื่องสำคัญ 3 อย่าง

1. **`x` และ `y` ไม่มี stack slot เลย** ไม่มีคำสั่งจองพื้นที่ ไม่มี `add` ทั้งฟังก์ชันถูกคำนวณล่วงหน้า (constant folding) เหลือแค่เลข `6`
2. บรรทัด `movl $6, 4(%rsp)` คือ วางเลข 6 ลง memory ซึ่งเกิดขึ้น**เพราะ black_box บังคับ** ไม่ใช่เพราะ binding ต้องการที่อยู่
3. นี่คือความหมายของ zero-cost abstraction โค้ดที่คุณเขียน (binding, expression, function call) หายไปหมด เหลือแค่เครื่องจักรที่เร็วที่สุดเท่าที่เป็นไปได้

ลองเปลี่ยนเป็นของตัวเองได้ที่ [godbolt.org](https://godbolt.org/) วางโค้ดด้านบน (แบบ `pub fn main()`) ตั้ง optimization เป็น `opt-level 3` กด compile แล้วเลื่อนดู assembly ของ `main` จะเห็น `movl $6, 4(%rsp)` เหมือนกัน

> 📌 **ถ้าไม่ตั้ง optimization (godbolt ค่าเริ่มต้นเป็น debug) จะได้ assembly คนละแบบ** `x` กับ `y` มี stack slot และมี overflow check
>
> ```asm
> example::compute:
>         sub     rsp, 24
>         mov     dword ptr [rsp + 16], edi   ; ← binding x อยู่บน stack
>         inc     edi
>         mov     dword ptr [rsp + 12], edi   ; ← binding y อยู่บน stack
>         seto    al
>         jo      .LBB2_2                     ; ← overflow check (x + 1 อาจล้น)
>         ...
> ```
>
> นี่คือบทพิสูจน์อีกชั้น **binding จะเกิด stack slot ก็ต่อเมื่อไม่มีการ optimize เท่านั้น** พอเปิด opt-level 3 แล้ว `x`/`y` จะหายไป เหลือแค่ `movl $6` ตามที่เห็นด้านบน

> 💡 **ทำไมต้องรู้เรื่องนี้?**
> เพราะมันอธิบายได้ว่าทำไม Rust ถึงฟรีไม่มีค่าใช้จ่ายแอบแฝง คุณได้ abstraction สูง แต่เครื่องจักรจริงทำงานด้วยราคาเท่า C ที่เขียนด้วยมือ [อ้างอิง: Rust Reference - Variables](https://doc.rust-lang.org/reference/variables.html)

---

## อ่านมาถึงตรงนี้ ต้องจำให้ได้ 3 ประโยค

1. **binding = ชื่อของค่า ไม่ใช่กล่อง** คอมไพเลอร์จัดการตำแหน่งให้เอง
2. **immutable by default + `mut` ชัดเจน = ให้ทั้งคอมไพเลอร์และคนอ่านรู้ว่า "อะไรเปลี่ยนได้"** แลกการพิมพ์ 3 ตัวอักษรกับการไล่หาบั๊ก 3 ชั่วโมง
3. **ตัวแปรตายเมื่อจบ scope** stack pop ทันที, heap drop ทันที ไม่มี GC ไม่มีการเดา

ถ้าเข้าใจ 3 ข้อนี้จริงๆ คุณจะไม่ได้แค่ใช้ Rust ได้ แต่จะเข้าใจว่าทำไมกฎทุกข้อของมันถึงต้องมีอยู่
